# How fast does the PicoCalc search when its Chess world executes from PSRAM?

After White plays e2–e4 in the PicoCalc Chess app, the engine chooses a reply. The playable configuration allows it to examine 1,600 positions. In this case it completes a search three half-moves deep, selects b8–c6 and assigns the position a score of 12. Both compiler versions returned that answer on the board. Across six matched repetitions, the median time to compute it fell from 241.011 ms with the old compiler to 206.723 ms with the promoted compiler. What work changed if the move, search depth and number of positions examined all stayed the same? [Observed timings and search results](../various/psram/physical.json)

## Where the instructions live

A PicoCalc *world* is an application component that the operating system loads and calls. For a native Typed world, the compiler emits RISC-V instructions for the application and links them into a reserved region of an executable file. The file includes support code that handles events and connects an app to operating-system services. The loader allocates memory, copies the loadable segments there and resolves addresses. On the playable ESP32-P4 profile that memory is external pseudo-static RAM, or PSRAM. The processor fetches the app's instructions through its cache. The location of code and data can influence elapsed time even if two runs execute the same instructions. [Playable loader configuration](../../../../../../picocalc-os/port/esp32p4/sdkconfig.smooth-chess)

An earlier study timed an extracted Chess engine whose instructions were linked directly into a test firmware’s flash-mapped code. It found that a small function which could keep its arguments and intermediate values in registers could omit the instructions that reserve and release a stack frame. A frequently called arithmetic helper could therefore cost fewer instructions per invocation. The promoted compiler includes this optimization and a second change. It carries a checked text access or literal write forward to native instruction selection, allowing the generator to use a direct checked address or reuse the address of a literal destination. The Chess engine represents its board using Typed buffer cells, so a source operation spelled `board.charCodeAt(...)` can lie on a search path. The present comparison changes both optimizations together. Separating their individual contributions in PSRAM would require additional compiler arms. [Earlier three-arm study](../../PICOCALC-NATIVE-WAVE--six-parallel-experiments-in-handheld-compiler-construction/analysis/03-leaf-lowering-and-selective-inlining.md) · [Search source](../../../../../../picocalc-os/worlds/chess/search.typed)

## Loading two complete worlds

The experiment used the shipped full Chess source, including its painter writer, and the same release reactor as a linker template for both compilations. The baseline compiler emitted 256,400 instruction bytes and the promoted compiler emitted 180,860. Both complete executable files occupy 274,892 bytes because both retain the same reserved slot. The compiler change reduces the amount of code occupying that slot by 75,540 bytes. This is a statement about the complete program. A search visits only some of its functions, so a percentage reduction in total generated bytes does not directly predict a percentage reduction in search time. [Exact application assets and links](../various/host/combined.json)

Before running a search, the probe passes one of these files through the same ESP-IDF ELF loader used to relocate native worlds. The linked file gives an address for the search initialization function and another for the slice function. Both files have zero as their lowest loadable virtual address. For each function the collector can therefore add its linked virtual address to the reported segment base and check that the result equals the pointer invoked by the probe. The pointers must also lie in the P4’s PSRAM window. This check ran at each of the twelve world loads, including each time the order of the two arms reversed. The board buffer and mutable search state were separately allocated in external RAM. [Entry address extraction](../scripts/psram/01-export.mjs) · [Collector checks](../scripts/psram/03-device.py)

## Holding the game’s work fixed

A *node* is a position examined by the search. A *ply* is one move by one player. A *slice* lets the engine do a bounded amount of internal work before yielding control to its caller. Calling a slice with a 48-step allowance does not mean it examines exactly 48 nodes. Some steps generate moves or restore an earlier board position. Keeping the node count and slice count in the oracle catches two different ways a run could finish sooner. All six pairs for each position agreed with a previously fixed Wasm execution on the selected move, score, completed depth, number of examined nodes and number of slices.

| Position | Requested depth | Node budget | Completed depth | Examined nodes | Slices | Selected move |
|---|---:|---:|---:|---:|---:|---|
| Opening | 3 | 30,000 | 3 | 871 | 41 | b1–c3 |
| Kiwipete | 3 | 30,000 | 3 | 7,194 | 453 | e2–a6 |
| After e2–e4 | 4 | 1,600 | 3 | 1,600 | 78 | b8–c6 |

The position after e2–e4 illustrates why checking the requested depth by itself would be insufficient. Both arms reached the node budget before completing the fourth ply. A run that reported depth three after examining 1,200 nodes would have done appreciably less work, even if it happened to select the same move. The board check catches another difference. During a search the engine moves pieces speculatively, evaluates positions and undoes those moves. At completion, the buffer capacity and all 135 root-position cells had to equal the initial fixture. Those cells include the piece placement and auxiliary state such as castling rights and the side to move. The unused working area beyond the root had no byte-equality requirement. ## Reading the elapsed times

The firmware timer starts immediately before `chessStartSearch`, calls `chessSearchSlice` until the engine finishes, and stops before checking the answer. It includes the native work and the short C loop that reads the running flag and counts slices. It excludes loading the ELF, preparing the fixture, compiling the source and steering the on-screen app through an input. This boundary allows a fixed position to be repeated at a known memory placement. Ordinary key-to-visible-reply latency also includes scheduling between slices, event delivery and rendering. [Timing loop](../scripts/psram/main/bench.c)

| Position | Stock median | Promoted median | Median paired reduction | Observed paired range | Reduction from arm medians |
|---|---:|---:|---:|---:|---:|
| Opening | 122.130 ms | 104.843 ms | 14.160% | 14.133–14.196% | 14.155% |
| Kiwipete | 1,344.083 ms | 1,154.323 ms | 14.117% | 14.110–14.126% | 14.118% |
| After e2–e4 | 241.011 ms | 206.723 ms | 14.227% | 14.211–14.265% | 14.227% |

Give each position its own comparison. In block `b`, denote the original time by `s_b` and the promoted time by `p_b`. The paired reduction is `100 × (1 − p_b / s_b)`. The headline reduction is the median of those six quantities. A second statistic divides the two separately computed median times. These numbers can differ because sorting each arm independently can put different blocks in its middle positions. The firmware alternated which compiler arm ran first in each block and rotated the three positions across runs. Six repetitions per case and arm gave 36 elapsed times in one boot, all at 360 MHz. The resulting range describes this board and schedule. The rows give no estimate of variation between boards or between boots.

The promoted program completed each of the eighteen matched searches sooner. The absolute savings depended on how long the position took to search. Kiwipete saved 189.760 ms by difference of arm medians. The shipped reply saved 34.288 ms by the same calculation. All twelve loads used the same segment base, `0x48008fc0`, although the compiler placed the individual search functions at different offsets inside each world. That common base limits one source of variation. Instruction address alignment, branch layout and cache behavior within each program are still part of the measured effect.

The earlier flash-mapped run reported about 7.4% for frameless leaves alone on the shipped reply. Here the promoted compiler combined late text lowering with frameless leaves and ran the complete world from PSRAM with its state also in external RAM. Subtracting 7.4% from 14.2% would mix differences in code generation, memory placement, harness and program extent. This trial supplies direct timing evidence for their combined release configuration. It cannot allocate a particular number of milliseconds to the changed text instructions, saved frame operations or memory system.

The physical result answers a narrower release question than full app qualification. It measures whether compiler changes carry over when the matching search functions execute from relocated PSRAM in their full Chess worlds. The ordinary app's interactive trials separately establish the response the user sees after a real input. Reading those measurements together distinguishes a change in the engine’s compute time from a change in how long the operating system takes to deliver and display the reply.
