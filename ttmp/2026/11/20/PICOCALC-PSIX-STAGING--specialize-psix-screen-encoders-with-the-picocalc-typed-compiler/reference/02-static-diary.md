# Declared encoder investigation diary

## Step 1 — Fix the input boundary and implement structural staging

I chose the existing Chess semantic payload to let the encoder consume pieces, move masks and metadata before a generic screen tree has been constructed. This keeps the application source of the values and the admitted PSIX object both observable. The main design problem was preserving the frozen encoder's lexicographic string order when both board and mask strings are live.

### Prompt context

The exact request is recorded in the [director diary §1](01-director-investigation-and-reading-diary.md). The parent task asked for a real producer-side shape-specialized encoder compiled by the existing Typed frontend and RV32 backend, proof through executed code, and a reproducible artifact suitable for hardware testing. I interpreted “blit” as exposing a counted packed byte span at the encoder's call boundary.

### What I did

- Audited the PSIX reference `encode()` and the earlier Chess `chessRender()` producer and its actual replay.
- Chose a standalone import-free interface with 90 argument cells. Board and mask hex strings come from numeric runtime data. Stage the shape and renderer identity in ordinary JavaScript, then run the Typed compiler on the resulting source.
- Changed the initial proposed output from one byte per cell to two bytes per cell after checking the physical call ABI with the board operator. Kept the high byte of an odd terminal cell unchanged and left both output and input untouched on a capacity failure.
- Implemented PSIX object and tuple offsets, finite binary64 emission for large integer holes, and dynamic string rank computation. Coordinated `psixGenerateSource(primitives, title)` and `psixEncode(input, out, capacity)` with the board harness.

### Why

Canonical v1 byte equality requires recalculating IDs when either variable string sorts before a fixed key. One frame's offsets can certify only values in that frame. A declared bounded shape puts facts such as the key set and tuple length into the staging pass, while keeping values live on every call.

### What worked

The first linked Typed source independently produced a Wasm module and an RV32 instruction image. The generic producer found by reading the BINARY ticket was independent enough to serve as a C oracle, with the frozen JS encoder as the primary wire reference.

### What needed revision

The initial compile failed with `SyntaxError: 39:24: expected return` in the Typed frontend. A single-line conditional body supports a return, and the primitive wrote an assignment without braces. Wrapping assignment bodies in braces fixed the syntax. The CJI standalone runner then failed to link with `03-rv32-driver.c:(.text+0x1ac): undefined reference to memset`. GCC used that symbol for an automatic zero aggregate. I made the invalid-input fixture static and zero-initialized, which removed the dependency from the freestanding wrapper.

### What I learned

Place all fixed-layout bodies before optional binary64 bytes. The first proof of this property was specific to the concrete shape. The independent reviewer asked that future changes enforce the invariant. The generator now rejects any fixed container placed after a potential wide integer in preorder. Adding the guard preserved the original generated bytes.

Read `chessShape()` and `stageShape()` in [the generator](../scripts/static/01-specialize.js), then compare the output contracts in the [design and replay guide](../design-doc/02-static-emitter.md).

## Step 2 — Verify executable bytes and measure host endpoints

I generated input from 127 real Chess replay events and used all 47 screen calls, including reset, promotion, both castles, en passant and signed search statistics. The synthetic suite exercised profile boundaries and both dynamic strings' lexicographic positions. All four encoders agreed on every tested packet.

### What I ran

I ran `node scripts/static/05-replay.mjs` with the four arguments in the design guide. The runner invokes the previous Chess replay, validates source output through Wasm, links the raw compiler-generated code in a C freestanding RV32 ELF and compares it in the CJI emulator. It also builds the old native C reference against cJSON and streams in the same payloads. It outputs board fixtures, native source, all nine host timing samples, and one emulated instruction count per vector.

### What needed revision

Node's synchronous launch of the emulator with default piped stdin reported `spawnSync .../cji/build/rv32/rv32emu EPERM` despite child status 0 and all 968 expected stdout bytes. Direct shell execution under the same sandbox returned the same 968 bytes with exit 0. Using explicit ignored stdin in the runner avoided that failure. The native C oracle reads its input from a file descriptor so its subprocess can remain synchronous.

### Evidence

- The CJI emulator returned after all 121 test vectors matched exact packed bytes, capacity refusal left bytes untouched and one bad input length was rejected.
- Wasm agreed on the same vectors, refused both insufficient byte budgets and insufficient backing cells, preserved output tail bytes and input cells, and rejected 15 malformed cases without writing.
- `"Pico Chess"` and `"chess"` each produced distinct RV32 images. Their generated Wasm encoders matched the JS reference. The second title reuses the existing app string, so the new dictionary contains one fewer entry.
- The receipt records the 16,680-byte typed source, 16,116 bytes of executable RV32 instructions and 6,514 Wasm bytes. The source and image digests were supplied to the board operator. [Host receipt](../various/static/host-receipt.json).

### What warrants a second pair of eyes

The bound check is meaningful only with trusted buffer headers and disjoint live allocations. The test's preloaded input and native output are the encoder endpoints. They exclude adapting the state from the game or shipping the bytes to the compositor. The host JavaScript reference allocates a new typed array and runs in a different execution engine from the specialized encoder.

## Step 3 — Integrate the physical evidence

The director's board harness used the frozen generator and Typed primitives. It staged the source on the physical ESP32-P4, required the linked artifact to match the host golden ELF, then invoked the relocated native entry. Each of seven blocks compiled afresh and rotated the hot arm order. The byte check ran independently after every measured call.

### Outcome

The generated native function matched the generic reference for all 47 traced states in each block. Its median call was 78.24 µs, against 101.28 µs for generic C and 24.71 µs for the resident C layout-table writer. Runtime generation through qualified load took 603.79 ms median. Those endpoints support a roughly 26,210-call break-even against generic C on the measured board and zero break-even advantage over the layout table. Restoration and its verification are tracked by the director. [Physical evidence](../various/physical.json).
