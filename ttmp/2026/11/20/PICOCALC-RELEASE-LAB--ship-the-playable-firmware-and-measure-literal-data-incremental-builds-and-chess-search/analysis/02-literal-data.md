# When the Compiler Emits Text as Instructions

The smooth Chess game embeds 16,316 bytes of painter source. Every byte has to reach the authorized painter loader unchanged. This experiment asks how the mobile compiler can generate that exact UTF-16 buffer while emitting less native code.

Authored by the commissioned tool-free Opus High research lead from the study's design and aggregate results. The experiment operator verified the numbers and edited the article against the source and receipts. [Original commissioned draft](../sources/literal/opus-high-article.md) [Design and reproduction](../design-doc/02-pool-checked-buffer-literals.md)

## How Typed emits the painter source

The complete Chess input is a 61,022-byte Typed source file. It contains the game and the generated routine that reconstructs the 16,316-byte painter. The direct RV32 backend initially allocated 256,400 bytes of native instructions for this program. The prototype emits 54,320 instruction bytes and 33,852 literal bytes. The main question is how long constant text became a substantial part of the program's machine code.

## The operation being compiled

Typed has a checked operation, `writeLiteral`, that writes a string literal into a UTF-16 buffer at a start index. A buffer is a 32-bit capacity followed by that many 16-bit code units.

```c
struct u16buf {
    uint32_t capacity;  /* count of u16 units that follow */
    uint16_t units[];   /* first unit sits 4 bytes after the buffer address */
};
```

A UTF-16 code unit is one 16-bit value. Most characters take one unit. Characters outside the Basic Multilingual Plane take a surrogate pair of two units. The operation copies code units exactly. A lone surrogate and a NUL each have an ordinary 16-bit representation.

The frontend fixes the semantics before any backend sees the operation. It evaluates the start expression exactly once. It then checks that the start position and the last position the literal will cover both fall inside the capacity. Nothing is written until both checks pass. An empty literal still evaluates the start expression and writes nothing. For a literal of n ≥ 1 units, the behavior matches this C sketch.

```c
uint32_t start = eval_start_once();
check_in_bounds(b, start);            /* traps before any write */
check_in_bounds(b, start + (n - 1));  /* traps before any write */
for (uint32_t i = 0; i < n; i++)
    b->units[start + i] = lit[i];
```

The checks happen before the literal writes any unit, and the copy uses the same checked range. Any side effects while evaluating the start expression remain observable when a check traps. The frontend saves the address used by the native path in a local.

## What the baseline backend emits

This backend emits fixed-width 32-bit RV32 instructions. An instruction can carry only a small constant. `addi` (add immediate) carries a signed 12-bit value, which covers −2048 through 2047. Larger values need `lui` (load upper immediate), which sets the upper 20 bits of a register, followed by an `addi` for the rest.

The baseline numeric backend lowers a constant literal with three steps per code unit. It loads the saved address, materializes the unit as an immediate, and stores a halfword. The sketch below shows one unit. Register names and offsets are illustrative.

```asm
lw    t5, SAVED(sp)    # load the saved address
addi  t6, zero, 0x41   # 'A' fits in the 12-bit immediate
sh    t6, OFF(t5)      # store 16 bits
```

A unit such as 0x4E2D does not fit in 12 bits. Materializing it takes `lui` plus `addi`, which makes four instructions for that unit. The baseline materializes each unit separately, including consecutive repeats. The floor is therefore three instructions, or 12 bytes, for every code unit of every literal. This is ordinary fixed-width RV32 code, and the floor is a property of this emitter.

That floor explains the Chess number. Text that occupies 2 bytes per unit in memory occupies at least 12 bytes per unit as code.

## Splitting a constant into upper and lower parts

The 0x4E2D case is worth working through, because the same arithmetic reappears when code has to find the pool. `addi` sign-extends its immediate. When the low 12 bits of the target are 0x800 or larger, `addi` treats them as negative, so the upper part has to be rounded up by one to compensate.

```js
// Split a 32-bit value into a 20-bit upper part and a signed 12-bit lower part.
function splitHiLo(value) {
  const lo = (value << 20) >> 20;  // sign-extend the low twelve bits
  const hi = (value - lo) >>> 12;
  return { hi, lo };
}
```

For 0x4E2D the low 12 bits are 0xE2D, which is above 0x7FF. The function returns hi = 0x5 and lo = −0x1D3. The pair `lui t6, 0x5` and `addi t6, t6, -0x1D3` produces 0x5000 − 0x1D3, which is 0x4E2D. Without the rounding, hi would be 0x4 and the sign-extended low part would subtract 0x1D3 from 0x4000. The result would land 4096 below the target.

## The pooled design

The change gives the backend a second way to lower a constant write. It applies only to a statically checked `writeLiteral` whose literal has at least 16 UTF-16 units. Shorter literals keep the baseline lowering. The existing 1022-unit limit on a literal is unchanged.

For a qualifying write, the frontend emits a private numeric op that carries two numbers. One is the index of the local holding the saved address. The other is the literal's ordinal. The backend appends the literal's exact code units, little-endian, to a literal pool in the direct RV32 image. The emitted site copies from the pool into the buffer at run time.

Before its loop, the site does three things. It loads the saved address and adds the four-byte payload offset, which skips the capacity field. It computes the pool entry's address with a PC-relative instruction pair. It computes where the source range ends. The loop then copies until the source cursor reaches that computed end.

Register discipline keeps the copy from disturbing the surrounding expression. The backend keeps live operand-stack values in t0 through t4 or in spill slots. The copy site uses only t5, t6, a0 and a1 as scratch, so whatever the enclosing expression has in flight survives the copy. The site makes no external calls and uses no instruction outside the native ISA.

## Finding the pool from code

The emitted site uses a relative address whose value survives relocation. It uses `auipc`, which adds a 20-bit upper immediate, shifted left by 12, to the address of the `auipc` instruction itself. An `addi` supplies the low part. Once layout is final, the assembler patches both immediates by applying the same `splitHiLo` rounding to the distance.

```asm
auipc t6, HI(entry - pc_of_auipc)
addi  t6, t6, LO(entry - pc_of_auipc)
```

The subtle point is the reference address. The reference address for both immediates is the address of the `auipc`. An implementation that measured the distance from the `addi` would compute an offset 4 bytes too small and produce an address 4 bytes before the entry. Every fixup in this design uses the `auipc` address.

These are module-local data offsets. As long as code and pool are placed together as laid out, the distance from a site to its entry is fixed at assembly time.

## The two copy loops

Both loops rely on halfword alignment of source and destination. The pool stores whole code units at even offsets, and the buffer payload sits at an even address.

The halfword variant loads 16 bits with `lhu`, stores 16 bits with `sh`, advances both cursors by 2, and branches back while the source cursor differs from the computed end.

```c
/* halfword variant, written as C */
const uint16_t *src = entry, *end = entry + n;
uint16_t *dst = payload_start;
do { *dst++ = *src++; } while (src != end);
```

The word variant moves 32 bits per iteration where it can, and it uses 32-bit accesses only at addresses that are multiples of 4. Source alignment is decided at compile time. The pool follows a code extent that the design assumes is aligned, so the emitter knows each entry's alignment when it appends the entry. Only entries at a naturally four-aligned offset get a fast arm. Other entries get just the halfword loop.

Destination alignment is decided at run time, because the start index is a run-time value. The fast arm tests the destination address. If it is four-aligned, the arm copies every complete word and then one trailing halfword when n is odd. Otherwise control falls into the halfword loop.

```text
# machine-level pseudocode for a four-aligned source
if destination % 4 == 0:
    for i in 0 .. floor(n / 2) - 1:
        store_word(destination + 4*i, load_word(entry + 4*i))
    if n is odd:
        store_halfword(destination + 2*(n - 1), load_halfword(entry + 2*(n - 1)))
else:
    copy_halfwords(entry, destination, n)
```

Little-endian order is what makes the word copy correct. Two adjacent units stored little-endian in the pool form a 32-bit word. Storing that word little-endian into the buffer puts each unit back at the same position.

The word variant adds code at sites whose entries already happen to be aligned. The data extent is the same for the exact-deduplication and guarded-word variants.

## Where the pool lives in the pipeline

The direct backend lowers functions as a stream, one at a time. After each function, its old numeric code and its literal string array are cleared. The emitted instruction words, the fixups still awaiting final addresses, and the pool are retained until layout. At layout the assembler places the pool, patches the `auipc`/`addi` fixups, and runs the existing import patching as before. The default Wasm backend and the closed slot entry are unchanged.

Exact deduplication is an option on the pool. When two qualifying writes use identical literals, both sites point at one shared entry.

The design guide states three assumptions. The code extent is aligned. Destination buffers are valid and disjoint from the pool. The pool depends on the loader keeping executable contents outside the writable regions it exposes to Typed.

## The size argument

Let n be the number of code units in a qualifying literal. Write B(n) for the baseline code and P(n) for a word-variant site plus its data. The design guide gives a maximum of 88 instruction bytes for a word-variant site before its data, and the pool needs at most 2 trailing padding bytes.

$$B(n) \ge 12n \qquad P(n) \le 88 + 2n + 2$$

At the threshold of 16 units, P(16) ≤ 88 + 32 + 2 = 122, which is below the baseline floor B(16) ≥ 192. The slopes differ, with at least 12 bytes per unit for the baseline and 2 for the pool, so the gap widens with length.

$$B(n) - P(n) \ge 10n - 90$$

At n = 16 the saving is at least 70 bytes, and each further unit adds at least 10. A deduplicated repeat pays no data at all, only its site. The bound follows from this backend's measured scalar encoding and fixed-width site instructions.

The experiment fixed the threshold at 16 and compares with the emitter used by the ordinary release, whose scalar code materializes each constant separately.

Chess has 33 pool references, all unique, so dedupe changes nothing. The halfword arm cuts the total from 256,400 to 88,172 bytes, a derived reduction of 168,228 bytes or 65.6 percent. The 33,852 data bytes hold 16,926 code units. At the baseline floor those units alone would have cost 12 × 16,926 = 203,112 bytes of code. The measured code reduction is 202,080 bytes, close to that floor. That closeness is what the size argument predicts when most of a program's code was long constant text.

Editor has 32 pooled uses, 31 of them unique. Halfword with exact dedupe cuts its total from 89,168 to 77,732 bytes, a derived 12.8 percent. Its occurrence pool holds 1265 units. At the floor those would cost at least 15,180 bytes, which is about 17 percent of its stock code. The saving is bounded by how much of a program is long constant text, and Editor simply has less of it. Dedupe removes 66 data bytes, which is one repeated 33-unit literal. The remaining unit count becomes even, so the 2 bytes of padding disappear too, for 68 bytes in all.

The held-out synthetic workload repeats one literal. Exact deduplication halves its pool data, saving 104 bytes.

The word variant costs code and nothing else. It adds 912 bytes in Chess, 856 in Editor and 80 in the synthetic case, with data unchanged.

## Correctness evidence

The native instruction model reconstructs the exact authorized Chess painter source. A separate differential compares complete test memory and return or trap outcomes with the stock Wasm backend. The matrix covers 180 success, trap, alias and single-evaluation cases. It also covers 48 cases that vary surrounding operand depth and alignment, plus three overlength rejections. Some inputs contain non-ASCII text, NUL, a lone surrogate and a surrogate pair.

Each category targets a specific risk. Comparing whole memory catches changed bytes outside the intended write and distinguishes the side effects of evaluating start from a partial literal write before a trap. Single-evaluation cases confirm that the start expression runs once. Operand-depth cases put live values in t0 through t4 and in spill slots around the write, which tests the scratch-register discipline. Alignment cases drive both the fast arm and the halfword fallback of the word variant.

The model interprets the generated RV32 words directly and checks access alignment. Streaming and buffered emission produced byte-equal output. The existing emitter input was validated by Typed, and the Wasm backend's byte output was identical to before.

## Compilation on the PicoCalc

The board was a revision 1.3 ESP32-P4 running CPU1 at 360 MHz with PSRAM at 200 MHz. The source text lived in PSRAM and went through the real on-device direct emitter and linker. Each call created a fresh QuickJS runtime on one firmware that was already running. Each workload ran five interleaved samples per arm, for 30 successful calls in total. The board receipt labels the arms stock, half and word.

| Workload | Arm | Median time (µs) | Median tracked heap (bytes) |
|---|---|---:|---:|
| Chess | stock | 5,254,907 | 3,181,936 |
| Chess | half | 2,659,192 | 1,681,944 |
| Chess | word | 2,677,218 | 1,692,172 |
| Editor | stock | 4,531,573 | 2,567,084 |
| Editor | half | 4,332,638 | 2,536,560 |
| Editor | word | 4,350,644 | 2,541,996 |

Each call includes creation of its QuickJS runtime, Typed processing, native assembly and slot linking. It ends before loading and running the result. The trial used an already-running firmware on all 30 calls. [Board receipt](../various/literal/physical.json)

For Chess, halfword pooling reduces the median time by 2.596 seconds, or 49.4%, and the peak tracked heap median by 1,499,992 bytes, or 47.1%. For Editor, those reductions are 0.199 seconds, or 4.4%, and 30,524 bytes, or 1.2%.

Chess stock took 5.247–5.283 s across five trials, versus 2.638–2.695 s for halfword and 2.632–2.683 s for word. Editor stock took 4.502–4.579 s, versus 4.326–4.366 s for halfword and 4.331–4.378 s for word. The two pooled ranges overlap within each workload, and all samples came from one warm boot.

Tracked heap fell by much more than the image. In Chess the heap reduction is about 8.9 times the image reduction, and in Editor about 2.7 times. The tracked heap therefore measures more than image bytes. The receipt measures complete compile calls, so the phase-by-phase distribution remains open.

## The isolated writer

A separate board experiment ran the three generated Chess source-writer blobs from flash-mapped text, with a reinitialized PSRAM destination. The harness warmed each writer, measured eight calls per sample and rotated the arm order over 11 samples. It checked all 16,316 written units, untouched tail cells and the buffer capacity after every batch. ## What the measured extent changes

The used Chess extent fell from 256,400 to 88,172 bytes with the halfword pool. This is a 65.6% reduction within its reserved slot. The measurements used the same 274,892-byte Chess ELF and 242,124-byte Editor ELF envelopes for every arm. Runtime loaded memory savings would require a smaller reservation and a separate measurement of the loader's allocation. The tracked heap figures above describe compilation, while the ELF figures describe what the compiler returns.

A release trial would also have to execute the candidate through the actual game loader. The placement must preserve the PC-relative distances and the alignment used by the optional word path. The live-loaded buffer has to reproduce the exact source for authorization, and the pool must lie outside writable Typed buffers. In that trial, the full game and painter can exercise the copy with normal cache placement. The main result here is the difference that one literal representation made to actual Chess compilation time and used image extent. Its effects on rendering or input latency require their own measurements.
