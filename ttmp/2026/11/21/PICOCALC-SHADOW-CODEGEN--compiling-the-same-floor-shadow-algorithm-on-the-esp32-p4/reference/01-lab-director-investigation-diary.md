# Lab director investigation diary

## Step 1: Freeze the comparison before choosing a compiler change

This study keeps the renderer’s shadow algorithm fixed and measures code generated by the compiler. The target is one scalar decision per visible floor pixel. The first protocol split device, compiler and validation responsibilities. At the user’s request I consolidated it under one Opus High researcher. I supervise the measurement, operate the single board and independently reproduce the results.

### Prompt Context

**User prompts (verbatim):** [Commission and subsequent steering](../sources/commission.txt).

**Assistant interpretation:** Preserve the C algorithm in ordinary Typed source, measure the cost of the generated loops and implement a general compiler improvement. **Inferred user intent:** Discover what makes the generated code expensive on the device without gaining speed by rewriting the ray tracer.

### What I did

Created the docmgr ticket and froze the candidate comparison. The retired validation lead pinned the original Chess source at 57b2d9f, built an independent reference score and defined positive and negative transfer workloads before seeing candidate measurements. I requested cancellation of the two extra research lanes and retained their completed preparatory work.

### Why

The amount of work in a shadow call varies by pixel and light position. Conditioning on the route through the algorithm is necessary to interpret an average. Six blocks in a real renderer can establish a reproducible difference for those linked images but cannot on their own attribute that difference to an individual instruction.

### What worked

The previous study provides a physical board harness with flash verification, twelve full-frame fixtures and a live trace service on port 3794. The existing prior shadow-only guard saved 2.2085 ms per complete frame on its own control. That prior result supplies a useful comparison.

### What didn't work

I initially assigned three departments to this sequential research decision. The user asked to consolidate. I kept a single Opus researcher and took over the device and independent verification work.

### What I learned

A same-layout C arm matters because the Typed workspace stores fields as checked halfwords, whereas the production C implementation uses structures, signed fields and separate arrays. A direct production-C time measures the combined effect.

### What was tricky to build

Natural floor pixels may examine several spheres before returning. Each isolated one-sphere case can have one precisely identified rejection or hit. Timing an entire natural three-sphere call and dividing indiscriminately would conflate paths.

### What warrants a second pair of eyes

Compare the complete sequence of boolean outputs and valid input checks outside the timing interval. Inspect non-shadow code and the negative-control primary pass when the general optimization changes other functions.

### What should be done in the future

Build and run the matched baseline, then choose a first implementation based on emitted operations. Test transferred code on the frozen Chess workload and record the on-device compile cost.

### Code review instructions

Begin at typedRayInShadow in the Typed ray tracer and in_shadow in raytrace_demo.c. Read the frozen transfer design and the director’s phase guide.

### Technical details

Source revision at freeze is 57b2d9f. The Type-to-machine pipeline streams one function at a time. The initial research baseline uses the previous public pie-empty option. The first prediction will distinguish guest instructions, P4 cycles per call and complete-frame time to PSRAM.

## Step 2. Establish a baseline that can distinguish language, layout and code generation

### Prompt Context

The [commission and staffing correction](../sources/commission.txt) apply. I took responsibility for measurements after closing two research lanes.

### What I did

Generated twelve Wasm frame streams, pinned their native source image and derived the expected shadow return for every visible floor pixel. Independently classified each visited sphere using its projected bounds and exact intersection. On the opening pose, 7,811 full predicate calls rejected all three spheres on X alone. The researcher reproduced 74,226 calls from the shadow loop into the same arithmetic helper and found GCC computes its result inline. I accepted one candidate for implementation.

### Why

A fast path taken thousands of times can matter more than the exact intersection arithmetic. Comparing complete C and Typed renderers mixes scratch representation, checks, code generation, and hosting. Three C/Typed layout controls can separate some of those effects on valid inputs.

### What worked

The opening native image matches the previous study's complete 10,332-byte binary by SHA-256. The twelve captures match an independent arithmetic classifier per pixel. The frozen Chess scorer agrees with the independently executed six-function Wasm module on three positions in both evaluation modes.

### What didn't work

The initial fixture generator invoked a nested git process in the restricted environment, which reported EPERM and printed the command's captured output. Repeating the same generator in the host execution environment produced the pinned inputs. An initial register-assignment candidate was superseded when the helper-call counts became available.

### What I learned

One short-circuit expression can call the same helper once or twice per sphere. A helper removed from the caller changes costs throughout the caller's hot route. A high count of stack references alone cannot identify the fastest transformation.

### What was tricky to build

The stride applies to the output plane, while the oracle masks index a fixed 160 by 160 grid. The harness preserves padding, uses C scalar RGB as a bytewise comparison, tests depth and IDs independently, and supplies the shade-only entry with previously computed planes. Native and halfword predicate inputs share PSRAM placement. Every predicate return is checked outside the timed batch.

### What warrants a second pair of eyes

Confirm the timing units and phase names, the common indirect-call loop in the isolated tests, and the absence of candidate calls in the shadow-only primary pass. Account for placement-sensitive effects when interpreting tiny differences.

### What should be done in the future

Capture the control first, then rotate the baseline, selected caller and all callers in a single diagnostic image. A separately prepared Chess position measures transfer.

### Code review instructions

Start with scripts/board/01-images.mjs for input contracts, scripts/board/bench.c for timer boundaries, and scripts/board/layout.inc for both C layout controls. Inspect the source and native image digests in various/board/baseline-images.json.

### Technical details

The previous comparison used pie-empty. Both candidate arms preserve that setting. A P4 cycle count is taken around a whole sequence of indirect calls; its denominator is the number of calls in that particular fixture and route.

## Step 3. Time the source-identical control, reproduce the host treatment, and start the paired trial

### Prompt Context

The [commission](../sources/commission.txt) requests a physical comparison and a report for a new student. The sequential researcher chose one guarded-return transformation after observing the opening frame.

### What I did

Built the diagnostic with ESP-IDF 5.4.2 and staged the exact known baseline image. Timed 80 predicate batches and 24 integration entries in visit 1. Rebuilt the three treatment images from the same ray source and pinned Chess definitions. Independently executed scripts/compile/04-correctness.mjs and compared its output with the researcher's saved receipt. The comparison was byte-identical for 744 cases.

### Why

An independent scalar C path reading checked halfwords controls for a large semantic and representation difference. The separate physical visit establishes a baseline with different linked addresses from the subsequent candidate trial. Only within-visit pairs estimate treatment effects.

### What worked

Opening natural shadow calls took 70.15, 82.46, 129.36 and 430.01 cycles per call for production C, same-layout unchecked C, same-layout checked C and baseline Typed respectively (medians of four timed batches). Opening integrated frames took 7,712.5 µs in C and 55,642 µs in Typed. The harness checked each boolean before timing. Visit 1 completed its verified restoration and reported application health.

### What didn't work

The incoming baseline measured more work than a simple change to arithmetic width could explain. Even the GCC halfword control with bounds checks used materially fewer cycles than Typed. The researcher's register allocation alternative remains unmeasured in this study.

### What I learned

The earlier GCC comparison had removed all helper calls. The experimental compiler removes 74,226 dynamic calls from shadow, while retaining 264,928 shadow bounds checks. Whole-frame host instruction counts move from 14,879,359 to 14,088,411 for shadow only. This predicts a time saving without equating instructions with cycles.

### What was tricky to build

The comparison needs both source-identical treatment images and the physical board's own compilation output. A fresh QuickJS runtime with a PSRAM allocation meter times each on-device compile and validates its returned bytes by length and FNV digest against the corresponding host image. Raw SHA-256 identities are available on the host.

### What warrants a second pair of eyes

The frame and isolated predicate use different arm-number tables. The JavaScript workbook maps them explicitly and rejects unmatched or duplicated blocks.

### What should be done in the future

Evaluate separate primary, shade and full-frame changes, and distinguish isolated compiler behavior from deployment across the rest of the module.

### Code review instructions

Review checkpoint e54409b for fixture acquisition, 36adac5 for baseline host evidence, and 3d18ebf for the optional compiler pass. The compact board receipt identifies the physically flashed image and the restored playable image.

### Technical details

The control visit uses four blocks on the default scene. The main visit uses six blocks on each of twelve fixed fixtures and separate one-sphere path strata. Counts and checksums are checked at import. The optional compiler policy is either true or a function selecting the caller by name.
