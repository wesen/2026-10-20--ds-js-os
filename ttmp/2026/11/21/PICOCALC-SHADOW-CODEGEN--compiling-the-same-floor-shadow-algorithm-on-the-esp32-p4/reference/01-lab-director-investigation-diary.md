# Lab director investigation diary

## Step 1: Freeze the comparison before choosing a compiler change

This study keeps the renderer’s shadow algorithm fixed and measures code generated by the compiler. The target is one scalar decision per visible floor pixel. The first protocol split device, compiler and validation responsibilities. At the user’s request I consolidated it under one Opus High researcher. I supervise the measurement, operate the single board and independently reproduce the results.

### Prompt Context

**User prompts (verbatim):** [Commission and subsequent steering](../sources/commission.txt).

**Assistant interpretation:** Preserve the C algorithm in ordinary Typed source, measure the cost of the generated loops and implement a general compiler improvement. **Inferred user intent:** Discover what makes the generated code expensive on the device without gaining speed by rewriting the ray tracer.

### What I did

Created the docmgr ticket and froze the candidate comparison. The retired validation lead pinned the original Chess source at 57b2d9f, built an independent reference score and defined positive and negative transfer workloads before seeing candidate measurements. I requested cancellation of the two extra research lanes and retained their completed preparatory work.

### Why

The amount of work in a shadow call varies by pixel and light position. Conditioning on the route through the algorithm is necessary to interpret an average. Six blocks in a real renderer can establish a reproducible difference for those linked images but cannot on their own attribute that difference to an individual instruction.

### What worked

The previous study provides a physical board harness with flash verification, twelve full-frame fixtures and a live trace service on port 3794. The existing prior shadow-only guard saved 2.2085 ms per complete frame on its own control. That prior result supplies a useful comparison.

### What didn't work

I initially assigned three departments to this sequential research decision. The user asked to consolidate. I kept a single Opus researcher and took over the device and independent verification work.

### What I learned

A same-layout C arm matters because the Typed workspace stores fields as checked halfwords, whereas the production C implementation uses structures, signed fields and separate arrays. A direct production-C time measures the combined effect.

### What was tricky to build

Natural floor pixels may examine several spheres before returning. Each isolated one-sphere case can have one precisely identified rejection or hit. Timing an entire natural three-sphere call and dividing indiscriminately would conflate paths.

### What warrants a second pair of eyes

Compare the complete sequence of boolean outputs and valid input checks outside the timing interval. Inspect non-shadow code and the negative-control primary pass when the general optimization changes other functions.

### What should be done in the future

Build and run the matched baseline, then choose a first implementation based on emitted operations. Test transferred code on the frozen Chess workload and record the on-device compile cost.

### Code review instructions

Begin at typedRayInShadow in the Typed ray tracer and in_shadow in raytrace_demo.c. Read the frozen transfer design and the director’s phase guide.

### Technical details

Source revision at freeze is 57b2d9f. The Type-to-machine pipeline streams one function at a time. The initial research baseline uses the previous public pie-empty option. The first prediction will distinguish guest instructions, P4 cycles per call and complete-frame time to PSRAM.
