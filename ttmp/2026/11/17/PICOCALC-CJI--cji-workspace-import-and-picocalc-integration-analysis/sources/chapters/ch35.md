# 35 · Compiling on the Board

Chapter 30 made a world compiled on the host into the module the board loads. Chapter 33 made the compiler a program cji can compile, and chapter 34 made that program small. This chapter puts the two together. The compiler goes into the board's firmware, a world's source goes in, and its code comes out running, with nothing but the firmware doing the work.

The board is still the emulator of chapter 29 with the firmware of chapter 30. Everything the board does here, the emulator does instruction by instruction. So the chapter can count what a compile costs on the board's core, and it checks what the board makes against what the host makes, byte for byte.

The results:

- **A world compiled on the board is the host's.** For flaky, snake, toplog, topstate and about, three things equal the host's: stage 1's SLIR on the board equals stage 0's on the host, the module that slas writes on the board equals the one slas-rv32 writes on the host, and the world's calls equal the recorded ones.
- **A small world compiles in 0.65 to 1.9 billion instructions**: 1.6 to 4.8 seconds at 400 MHz and one instruction per cycle. snake takes 8.6 billion. Assembling and loading the module add under 1% to that.
- **A compile holds 8.5 MB at its peak** and almost nothing after. A compile that would need more than its cap is refused, and the firmware carries on.
- **The compiler is 4.19 MB of rv32 code**, a third of what it was, because identical functions are now emitted once.
- **Software floating point is counted as code.** It adds 7 to 11% to a compile, after chapter 34's integer paths had removed most of it.
- **One question is left for the board:** where in its flash the compiler lives.

## 35.1 The grammar

Nothing changes in programs. The firmware gains a service: given a world's source, compile it, assemble it, load it and start it. The test harness gains two modes:

```
COMPILE=1 sh tools/rv32/nw-test.sh   stage 1 on the emulator compiles each world; its SLIR must be stage 0's
BOARD=1 sh tools/rv32/nw-test.sh     the whole path in one firmware: SLIR, module and calls must be the host's
slas-rv32 -S --rootstack-slack BYTES  a larger slack past a world's checked root stack (stage 1's frames reach 2.8 KB)
```

## 35.2 What runs where

| piece | built by | where it lives |
|---|---|---|
| stage 1, the compiler | stage 0 writes its SLIR once; slas-rv32 assembles it | the firmware |
| slas for rv32 | the firmware's C compiler, once | the firmware |
| the runtime, the glue, the world runtime's unit and its export list | as in chapter 30 | the firmware |
| a world's module | slas, on the board, into memory | PSRAM, loaded from that memory |

**The compiler is part of the firmware, not a module.** Stage 1 is a program with a `main`, not a world. It does not speak the kernel's tables of chapter 30, and the kernel would call it as a service, not schedule it. Its code is megabytes, far beyond any world's allowance, and a module is copied into PSRAM each time it loads. Firmware code instead runs from flash through the cache. So stage 1 is assembled once by slas-rv32 into a relocatable object, and the firmware's build links it like the runtime's unit. None of chapter 30's assumptions about elf_loader apply to it.

**slas writes a module into memory.** slas-rv32 is a cross-assembler: it never runs what it makes, and what it makes does not depend on where it runs. Built for rv32 and run in the firmware, the same code writes the same module into a buffer. The firmware then loads that buffer the way elf_loader loads any module from memory. So a world compiled on the board is loaded and run exactly as one compiled on the host, and the board has only one path for native worlds.

The alternative was a JIT on the board, running code where SLJIT writes it. That would be a second path, with its own data layout and memory that is both writable and executable, which chapter 26 already ruled out for worlds on the board.

**Units, and no snapshot.** A world is compiled alone against the world runtime's unit (chapter 32). The unit is in the firmware, and its export list is data there too. The module writer finds `$nwInit` and `$nwEvent` in that list, so the board never needs the unit's text. A world compiled on the board has no snapshot. Taking one means running `main` at build time, which the board could do, but that is a step of its own. Such a world runs `main` when it starts, as chapter 30's no-snapshot mode already checks.

## 35.3 The compiler's natives on the board

Stage 1 talks to the outside through the natives of chapter 33: read the source, write the SLIR, spill a function, read an argument. They use the C library's stdio, and the board's C library, newlib, has the in-memory files they need. So runtime.c does not change; the firmware gives the natives buffers through stdio:

- **source:** the firmware registers the world's text under a name, and `fopen(name)` opens it as a read-only memory file;
- **SLIR:** while stage 1 runs, `stdout` points at an `open_memstream` buffer;
- **spills:** `tmpfile()` is a memory file. On the board it could be a file on the SD card instead.

The test firmware's small C library gained the same: a FILE that is either a descriptor or a growable buffer, with `fmemopen`, `open_memstream`, `tmpfile`, `fopen` over registered buffers, and the reads, writes and seeks over them.

A compile runs in its own runtime state and frees its heap afterwards. slas runs inside a malloc region of its own, which is freed when it returns, so whatever slas leaves behind goes with it. slas's exit, on an error, returns to the firmware instead of ending it. After the whole path the firmware keeps only the world's module and its heap: 43 KB for toplog, 124 KB for snake.

## 35.4 The check

For each world, three equalities:

1. Stage 1 on the emulator compiles the world as a unit. Its SLIR must equal stage 0's on the host (`cji.js W --world-unit --emit`), byte for byte.
2. slas on the emulator assembles it into a module, with the call to `$main$prelude` inserted that tools/link-units.mjs inserts on the host. The module must equal host slas-rv32's from the same text, byte for byte.
3. The firmware loads the module and sends the world its events. Its calls must be tests/native/NAME.out, which the host build makes.

The second is new. It means the board needs no trust of its own in slas: what it writes can be compared with the host's, and it is the same file.

All three hold for the four worlds of tests/native, and for about, whose start makes the same calls as on the host's fake kernel. The modes run on every later change.

A compile that would exceed its budget must be refused rather than stop the firmware. The firmware sets the runtime's fatal hook (chapter 30) around a compile. snake compiled with a 1 MB heap cap stops with "the compile was refused: out of memory: the heap would grow past its cap". The firmware goes on, and 176 bytes stay in malloc's blocks.

This found a bug in the collector. When the heap had to grow past its cap, the copying collector had already freed the old space before the cap check ended the compile. On the host, the program then exited and nobody noticed. On the board, the firmware continues after a refused compile and would have found a heap pointing into freed memory. The old space is now freed only once the new one exists.

## 35.5 One body per canonical name

Stage 1 was 12.7 MB of rv32 code, twice its 6.45 MB on x86-64, because a 64-bit word on a 32-bit core takes a pair of instructions for most operations. A census of the code found where it went. 69% was library instantiations (chapter 15): 7,328 copies of library functions, made for the compiler's own calls. And 9,275 functions, 4.08 MB of the x86 code, were byte-identical to another function.

Chapter 28's canonical names already say when two functions are the same. A function's canonical name is its base name and a hash of its text with the names of its callees. Copies of one function share it, apart from a suffix (`x2`, `x3`) that keeps names unique. So the build now emits the first function of each group and no others. Calls, tail calls and function references to a copy go to that first function.

Identity needs care. A static closure (chapter 8) is a function's value: two copies merged into one body must not merge two closures a program could compare. So two copies are merged only if they take the same static closures. The groups are split until each member refers to the same group, or the same function, at every reference. A copy whose own static closure is taken stays under its own name, as a stub of one instruction that tail-calls the shared body. `main` and the world's entries are never merged.

Neither the compiler nor any test takes a copy's static closure, so no stub exists today; a synthetic test checks the stub path on the interpreter, slas and the emulator. No new SLIR directive was needed, and slas did not change.

| stage 1 | before | after |
|---|---|---|
| functions | 10,855 | 1,627 |
| SLIR | 25.0 MB | 7.85 MB |
| x86-64 code | 6.45 MB | 2.22 MB |
| rv32 code | 12.7 MB | 4.19 MB |

Of all the work since chapter 32, this is the one change made on purpose to change the compiler's output. The 120 reference programs that have copies changed. The 167 without copies stayed byte-identical. Every program behaves the same, and stage 1 = stage 0 on all of them. Worlds shrink too: agenda's module by 9%, agent's by 3%.

## 35.6 Numbers without a double unit

The board's core has single-precision floating point but no double (chapter 34). Every double operation is a call to a helper: `__adddf3`, `__muldf3`, the comparisons and the conversions. Chapter 29's test firmware answered those helpers with a host call, one emulated instruction each, so their cost was invisible.

The firmware now has its own soft-float in C. It covers double add, subtract, multiply and divide with round-to-nearest-even; the comparisons; conversions to and from 32- and 64-bit integers and float; the 64-bit integer divisions; and floor, ceil, trunc, round and fabs. It matches the host's hardware bit for bit on two million random and edge-case inputs per operation: signed zeros, subnormals, infinities, NaNs, halfway cases. Every test firmware links it, so every count in this chapter includes it. On the real board the helpers would be libgcc's, with different costs and RISC-V's canonical NaN.

| | soft-float as code | as host calls | difference |
|---|---|---|---|
| flaky's ping | 16,853 | 14,787 | +14% |
| a snake tick | about 587,000 | about 531,000 | +10.5% |
| a world compiled on the board | | | +7.0% (toplog) to +10.7% (about) |

Chapter 34's integer paths are why the compile's share is that small. Before them, the same compiles took 753.6 M instructions for toplog and 10.24 G for snake. toplog's calls to floor and trunc alone fell from 0.6 million to 29. A compile still makes 0.68 million helper calls for toplog and 9.9 million for snake.

## 35.7 What a compile costs

Instructions on the emulated board, with soft-float as code; at 400 MHz and one instruction per cycle, 400 million instructions are a second:

| world | compile | slas | load | compile at 400 MHz |
|---|---|---|---|---|
| toplog | 646 M | 1.5 M | 0.2 M | 1.6 s |
| flaky | 1,133 M | 4.3 M | 0.3 M | 2.8 s |
| topstate | 1,212 M | 3.3 M | 0.4 M | 3.0 s |
| about | 1,917 M | 10.1 M | 0.9 M | 4.8 s |
| snake | 8,628 M | 31.9 M | 1.3 M | 21.6 s |

The compile is 99% of the path. Of a compile's instructions, the runtime takes 49%, stage 1's own code 40%, soft-float 7% and the C library 4%. Dynamic property access leads the runtime's share, as chapter 34's profile found on the host.

One instruction per cycle is the best case. The core is in-order, its instruction cache is 16 KB, the compiler is megabytes of code, and the heap is in PSRAM, so real compiles will be slower by a factor this emulator cannot measure. The board's own clock is the next measurement.

The compile's peak is 8.46 MB of malloc's blocks, 8.59 MB for snake. That is two 4 MB semispaces during a collection; the live data are 0.93 MB, and 1.43 MB for snake. Chapter 34's compacting collector would halve the peak, but the board's glue does not yet switch it on. slas holds 0.30 to 1.11 MB at most.

## 35.8 Where the compiler lives

The board has a 32 MB flash chip, of which ESP-IDF addresses the first 16 MB. Its partitions give the firmware a 4 MB application partition, then 128 KB of world records and a 12 MB FAT partition for files. A firmware that compiles holds, beyond picocalc-os's own image:

| part | code + data |
|---|---|
| stage 1 | 4,186,144 + 263,256 bytes |
| the world runtime's unit | 193,424 + 7,424 |
| slas and SLJIT's RV32 backend | 63,864 + 58,468 |
| the runtime and the glue | 92,440 + 2,090 |
| the unit's export list | 7,888 |
| picocalc-os's application today | 2,207,776 (Wi-Fi build) |
| **total** | **about 7.1 MB** |

Stage 1 alone is 255 KB over the 4 MB partition. Three ways out:

**A. Repartition.** Stage 1 stays in the firmware, as it is on the emulator. An 8 MB application partition takes 4 MB from the files partition. No code changes, but the board's layout does change, and every firmware update writes 7 MB.

**B. Read the compiler from storage for each compile.** The firmware keeps the runtime, the unit, slas and a loader: 452 KB of code without stage 1. Stage 1's relocatable object is a file on the SD card or the FAT partition. When a compile is asked for, it is read into one PSRAM block, relocated, used and freed. A prototype of this was measured on the earlier, 12.7 MB stage 1, compiling toplog and snake with SLIR and module equal to the host's:
- it read 13.08 MB from storage;
- it applied 4,883 relocations and resolved 133 names in 0.88 million instructions, 0.1% of the smallest compile;
- PSRAM peaked at 21.5 MB with the compile.

Scaled to the one-body stage 1, that is an image of about 4.45 MB and a peak of about 13 MB. At an assumed 10 to 20 MB/s from the SD card, the read is 0.2 to 0.5 seconds per compile. On the board the block must be executable PSRAM with its instruction cache made coherent, as elf_loader does for modules. The board's layout does not change. The prototype is kept in the ticket but not built into main, because the choice is the user's.

**C. A smaller compiler.** About 0.26 MB less and stage 1 fits the partition alone. About 3 MB less and it fits beside picocalc-os's application. Chapter 34 lists where the code still is: the runtime's dynamic paths and the compiler's own functions. C combines with A or B.

## 35.10 Against the real project

**What is done.** A cji world can be compiled where it runs, by the same compiler that compiles it on the host, into the same bytes. The pieces are the ones the earlier chapters built:
- a self-hosting compiler (chapter 33) that compiles a small world in a few megabytes (chapter 34);
- worlds as modules the board's loader takes (chapter 30);
- an assembler that writes the same module wherever it runs (chapter 29).

**What only the board can say.** How long a compile really takes, with PSRAM and a 16 KB cache. Whether elf_loader does what chapter 30 assumes. Whether the board's libgcc helpers cost what this soft-float costs. And how a compile service sits beside running worlds in 32 MB of PSRAM.

**What needs deciding.** Where the compiler lives in flash (§35.8). And which worlds may be compiled on the board at all: every world, only those named in the manifest, or only in a developer mode. A world compiled on the board is native code, so the choice is about trust, and it is the project's to make.

## Exercises

1. Stage 1's `--stats` reports each pass's time. Run a board compile with it and split the 646 M instructions of toplog's compile by pass. Which pass would a smaller board compiler drop first?
2. slas.c keeps state in static variables, so a firmware calls it once per boot. Reset them between runs, and compile two worlds in one firmware without a restart.
3. The board compiles a world without a snapshot. Run its `main` on the board after the compile, take the snapshot there, and write it into the module. What does the snapshot cost, and what does it save at each start?
4. Option B reads 4.45 MB from storage for each compile. Keep the image in PSRAM between compiles while memory allows, and free it under pressure. When is that worth its PSRAM?
5. Switch the board's glue to the hybrid collector of chapter 34, with the compile's memory as its limit, and measure the compile's peak and time.
6. Group functions by hash alone, across base names, and measure what §35.5 leaves on the table (lane 5 counted 39 copies kept apart by their names).

## In SPJ

SPJ's design names three places a compiler could run: on the build host, on the P4 when a world starts, and in a browser (chapter 32). This chapter is the second, built from the first. It is the same compiler, compiled by itself, assembled for the board, and checked against the host by comparing what both make. SPJ's design also describes `engine: "auto"`: compile a world at install, cache the result by source hash and compiler version, and run it in QuickJS when the compiler rejects it. Every piece of that now exists except the cache and the policy. Those are the kernel's, and the decision about which worlds may use them is the project's.
