# 30 · Worlds on the Board

Chapter 29 taught cji to write code for the board's processor. slas-rv32 wrote an ELF *relocatable* object, and an emulator linked it against a test firmware and ran it. That proved the code. It did not put a world on the board, because picocalc-os does not load relocatable objects. Its native worlds are ELF *shared objects*, relocated into memory by Espressif's elf_loader, entered once, and called afterwards through two small tables of function pointers. This chapter makes a cji world into that module.

The rule from chapter 29 holds: no C compiler when a world is built. A world's module comes from cji and slas-rv32 alone. The runtime is C, but it is compiled once, with the firmware. So the chapter's first question is where each piece lives (§30.3). The rest follows from the answer: the module's layout (§30.4), how its tables meet chapter 24's protocol (§30.5), chapter 27's snapshots and chapter 28's shared unit on rv32 (§30.7, §30.8), and what a world costs the board in memory (§30.9, §30.10).

The board itself is not here. elf_loader's source is not on this machine either. So the module is tested on the emulator, loaded the way the loader is documented to load, by a fake kernel that speaks the same tables. Every assumption made about the real loader is written down, so that it can be checked on the board (§30.6).

The results:

- **A world is a module the board's loader takes.** `slas-rv32 -c NAME.so --module` writes it, with no linker and no C compiler. `llvm-readelf -a` reads every module without a warning.
- **Four worlds make exactly the host's calls** on the emulator: flaky, snake, toplog and topstate, without a snapshot, with one, as units against the runtime's unit in the firmware, and all four in one firmware. Without the state swap, three of the four go wrong, as chapter 28 found.
- **A module built from C the board's way**, with clang and ld.lld, loads and runs through the same loader and kernel.
- **Small modules.** flaky is 171 KB loaded on its own, 88 KB with a snapshot, and 10.5 KB as a unit, of which 4 KB is its own code.
- **A world's memory is charged to the world.** Everything the runtime allocates for a world goes through that world's module, and a runtime error crashes only that world. A small world takes 48 KB of its 320 KB allowance.
- **The root stack is checked**, for no cost, and is 4 KB by default instead of 64.

## 30.1 The grammar

Nothing changes in programs. slas-rv32 gains options:

```
slas-rv32 -c NAME.so --module [--snapshot NAME.snap] [--extern unit.list] [--rootstack BYTES] NAME.slir
slas-rv32 -c prelude-unit.o --lib prelude-unit.list prelude-unit.slir
slas --snapshot-out NAME.snap NAME.slir
```

`--module` writes the shared object. `--snapshot` lays out a snapshot that the host's slas took with `--snapshot-out` (§30.7). `--lib` assembles the world runtime's unit for the firmware and lists its exports, and `--extern` builds a world against that list (§30.8). `--rootstack` sets the world's root stack (§30.10).

## 30.2 What picocalc-os does

picocalc-os runs most worlds in QuickJS. A world whose manifest says `"engine": "native"` is machine code instead, which talks to the kernel through the native-world interface of chapter 24: on the Linux host a process, on the ESP32-P4 an ELF module. Its SDK header, `sdk/nw_elf.h`, defines the module's contract. A native world is an ELF32 shared object for RISC-V with the single-float ABI. The firmware loads it with elf_loader, which copies its loadable segments into one block of PSRAM, applies its relocations, and calls its entry once:

```c
app_main(2, argv);   /* argv[0]: the kernel's table, argv[1]: the module's, which the entry fills in */
```

The kernel's table has two functions. `call` makes one system call, with the arguments of chapter 24's CALL frame: an operation, two integers, a 64-bit value and three strings. `error` says why the last call failed. The module's table also has two: `init`, called once, and `event`, called for every event with its kind, its strings and its JSON. `event` returns 0 when it is done and 1 when it will answer later. Anything else is a broken protocol, and the kernel crashes the world.

A module may use only the names the firmware's resolver gives it: 22 C library functions, among them the allocation functions, which charge the world, and 30 libgcc helpers. Any other name fails the load with "it links to X, which picocalc-os does not give a module". A world's allowance, `mem_kb`, must cover the loaded block (`segment_size`) and everything its module allocates.

## 30.3 Where the runtime lives

cji's runtime is about 2,900 lines of C, plus the world runtime compiled as a unit (chapter 32). A world's own code calls into both all the time. The resolver offers no maths library and no stdio, both of which runtime.c uses. So the runtime cannot simply be linked into each module as a prebuilt blob. Each module would have to carry its own C and maths libraries, compiled for the board, and slas-rv32 would need a real static linker for the dozen relocation types clang emits. Each world would also carry its own copy of the runtime, which is what chapter 28 removed, and pay for the copy out of `mem_kb`.

The runtime goes into the firmware instead, as chapter 29 decided. The firmware holds runtime.c, compiled once by the firmware's own build. It also holds a small C file, `runtime/cji_elf.c`, the glue between the tables and the runtime. With units, it holds the world runtime's unit, assembled once by `slas-rv32 --lib` and linked like any other object. A module names what it uses from these, and the firmware answers through a generated table (`cji_resolve[]`). The resolver would search that table after its own list.

That is the only change picocalc-os's code would need to load cji worlds: link three objects, and search one more table in `resolve()`. The loader, the kernel's table and the module's table stay as they are.

## 30.4 The module

slas-rv32 writes the whole file itself. File offsets equal virtual addresses, so the segments need no padding between them, which is the shape GNU ld gives with `max-page-size=16`:

| segment | flags | contents | relocations into it |
|---|---|---|---|
| 1 | R | ELF and program headers, `.dynsym`, `.dynstr`, `.hash`, `.rela.dyn` | none |
| 2 | R X | the world's code, then three entry thunks | none |
| 3 | RW | `.dynamic`; the table of outside addresses; static strings, shapes, closures; the snapshot; the world block | the table and every pointer word |

**No relocation in the code.** As in chapter 29, code reaches the table of outside addresses relative to itself, through an `auipc`/`addi` pair patched once the layout is known. The table has moved from the end of the code to the start of the writable segment. So the executable segment is never written, and the module needs no text relocations.

**Two kinds of relocation.** A word that points into the module, such as the address of a function or a string, is `R_RISCV_RELATIVE`, with the target's address as the addend. A word that names something outside, such as a runtime function, a soft-float helper, a symbol of the shared unit or the glue, is `R_RISCV_32` against an undefined name, with addend 0. The module never names its own symbols in a relocation. elf_loader 2.0 sends every named relocation to the firmware's resolver, even for a name the module defines; that is fixed in 2.1, according to its changelog. Every relocation target is 4-byte aligned, as 2.0 requires. A pointer in data is the low half of a 64-bit word (chapter 29), and the high half stays zero.

**The thunks.** The board calls three functions in the module: `app_main`, `init` and `event`. Each is eight instructions. It puts the address of the module's world block in a register, stores it in a global of the glue's, and jumps to the glue's function of the same purpose with every argument register untouched. The glue reads the global once on entry. Passing the block as an extra argument would have been simpler to read, but `event` already has eight arguments, and a ninth would go to the stack and need a frame in the thunk.

**The world block** is the module's description of itself, at offsets that the writer and the glue share through a header, checked at compile time and again at load time:

| word | holds |
|---|---|
| abi, size | a version and the bytes reserved, checked by the glue |
| snapshot, main | the snapshot if there is one; `main` if there is not |
| init, event | `$nwInit` and `$nwEvent`: the module's own, or the shared unit's |
| error_shape | the Error shape: the module's or the unit's |
| init_thunk, event_thunk | the module's two entries, for the module's table |
| malloc, realloc, free | the allocator to use for this world (§30.9) |
| rootstack | the root stack's size, chosen at build time (§30.10) |
| state | space for the world's `struct rt_state` (chapter 28) |

The same slas.c writes both kinds of object, so splitting its writer in two was checked the usual way. The relocatable objects chapter 29 tests with stayed byte-identical: 36 sample objects compared before and after.

## 30.5 The tables and chapter 24's protocol

The kernel's `call` has exactly the signature of the runtime's `rt_kernel_call`, the function behind `$call` in chapter 24's world runtime. That was no accident: both were written to carry the arguments of the wire's CALL frame. So the glue installs the kernel's two functions as the runtime's hooks, and nothing translates. A world's `$call(op, a, b, s0, s1, s2)` reaches the kernel's function directly.

The glue has three entries, one per thunk:

- `cji_elf_entry(argc, argv)` checks the block's version and size, keeps the kernel's table, and fills the module's: `{NW_ELF_ABI, init_thunk, event_thunk}`.
- `cji_elf_init()` swaps the world's state in, installs the kernel's hooks, and seeds Math.random from the world's name, as chapter 24 does. It then starts the runtime, loads the snapshot or runs `main`, calls `$nwInit`, and swaps the state out.
- `cji_elf_event(...)` swaps in, fills the runtime's event record, calls `$nwEvent`, swaps out, and returns 0 or 1.

Every call swaps the world's state (chapter 28), with a shared unit or without one. The runtime in the firmware is shared by every compiled world, so the swap is always needed.

A world whose handler throws is crashed. The module's table has no way to say so: `event` can only answer done or later. The glue returns 2, which the kernel treats as a broken protocol and crashes the world. The outcome is right, but the reason the kernel reports is wrong. The change belongs in picocalc-os: a value in `nw_elf.h` that means "crashed".

## 30.6 What the board's loader is assumed to do

elf_loader's source is not on this machine. What is known about it comes from picocalc-os's own diary of its native worlds, which records what elf_loader 2.0.0 does, and from the component's changelog. The module is built to satisfy the narrowest reading of both, and the design lists fifteen assumptions, each with its source. A few of them:

| assumption | source |
|---|---|
| ELF32, RISC-V, single-float ABI | picocalc-os checks this itself |
| one block from the first loadable segment to the end of the last, gaps zeroed | the diary; the zeroing is assumed |
| exactly three relocation types: `R_RISCV_32`, `R_RISCV_RELATIVE`, `R_RISCV_JUMP_SLOT` | the diary |
| a relocation target that is not 4-byte aligned fails the load | the 2.0.0 changelog |
| a named relocation goes to the resolver even when the module defines the name | assumed, from the 2.1.0 changelog |
| the loader writes the data cache back before the entry runs | the diary; not checkable here |

The emulator's new loader does what the list says and no more. It copies the loadable span into one block and applies only the three relocation types, refusing a misaligned target. It resolves names only through a table that the firmware itself carries, generated from picocalc-os's own lists of names plus the runtime's objects, and it stops at the first missing name with the board's message. A loader stricter than the real one is the safe direction: a module that loads here loads on any loader that does at least this much.

The loader was cross-checked the other way too. A small C module, built the way picocalc-os builds its native worlds (`clang -fPIC -fvisibility=hidden`, linked by `ld.lld -shared -z max-page-size=16` with the SDK's `nw_elf.c`), loads and runs through the same loader and the same fake kernel.

## 30.7 Snapshots on rv32

Chapter 27 takes a snapshot by running a world's `main` at build time, inside slas, and writing the heap it built into the object. slas-rv32 cannot run its own code. But the snapshot does not depend on the machine. The heap is 64-bit words on both machines (chapter 29), and every pointer out of it is either named — a function, the text of a string or shape, a static closure — or an offset into the block.

So the snapshot is taken by the host's slas and laid out by slas-rv32. `slas --snapshot-out NAME.snap` runs `main` as chapter 27 does and writes the snapshot as text: the words, the map of which words are pointers, the two entries, and one line per named reference, with its offset, kind and name. The output is deterministic. `slas-rv32 --snapshot NAME.snap` reads it into the structures chapter 27's writer uses, prunes the functions the snapshot made unreachable exactly as slas does, and lays the block out with relocations instead of names. Both programs are built from runtime/slas.c, so no C compiler runs per world.

The snapshots are the same size as chapter 27's on x86-64: 211 words for flaky, 1,628 for snake. All four worlds make the host's calls with and without them. toplog, whose start cannot be snapshotted, gets none, as on the host.

One consequence is worth stating. A value that `main` computes with a maths function, say a `Math.sin` at the top level, is computed by the host's maths library when a snapshot is taken, and by the board's when there is none. The same is true of chapter 27's snapshots on the host today, and none of the test worlds computes anything of the kind.

## 30.8 The shared unit on rv32

With units (chapter 32), the shared unit is the world runtime's unit itself, built once so that a world compiled later links against it unchanged. On rv32 it goes into the firmware. `slas-rv32 --lib` assembles it into an object of 191,706 bytes of code with 422 exports, which ld.lld links into the test firmware like any other object. The exports enter the resolver's table.

A world compiled as a unit names the unit's functions and data instead of carrying them. Its world block's `init`, `event` and Error shape name the unit's symbols too. All four worlds built this way make the host's calls.

Then four worlds go into one firmware, each loaded through its own tables, with their events interleaved the way chapter 28's multi-world test interleaves them. Every call finds the runtime holding another world's state, so every call depends on the swap. All four make their own calls. The control is the same run with a glue that does not swap the state, and in it three of the four go wrong. topstate, started last, is right, because the runtime still holds its state. That is exactly what chapter 28 found on the host.

## 30.9 A world's memory

On the board a world pays for two things: its loaded block, and the blocks its module allocates. Until this chapter, the runtime allocated a world's heap, root stack and call buffers with the firmware's own `malloc`. That memory was charged to no world, and it was never freed when a world was crashed and unloaded.

The fix needs nothing from picocalc-os. The runtime now allocates everything that belongs to one world through three function pointers, `rt_malloc`, `rt_realloc` and `rt_free`, kept per world in its state. That covers the heap's spaces, the root stack, the call buffers and the temporary UTF-8 copies. The world block names `malloc`, `realloc` and `free` as words to be relocated by name. The board's resolver already answers those names with its charging allocator, and the glue hands the three to the runtime for that world. What the runtime keeps for every world, such as static strings, stays the C library's.

The runtime's fatal errors used to end the process: running out of memory, a heap past its cap, an index out of range. On the board that would stop the firmware, not the world. Each now goes through a hook, `rt_fatal`, which the glue sets to end the world's turn with a crash. A snapshot whose `main` hits one of these now simply gets no snapshot, instead of stopping slas.

The fake kernel charges allocations as the board does, refuses past `NW_MEM_KB`, and reports each world's figures. Four worlds and a memory hog share one firmware at 320 KB each. The hog crashes alone, at its third request, with "crashed: out of memory" in its log, and the other four carry on unchanged.

## 30.10 The root stack

Measured that way, a small world's blocks came to about 99 KB, and 64 KB of that was its root stack, the stack of slots that hold its pointers for the collector (chapter 6). The four test worlds use 240 to 376 bytes of it. The emulator found that by watching stores into each world's root stack range.

Nothing in a program chooses that size. The embedder does, when it starts the runtime, and every embedder passed 64 KB. A root stack cannot grow once a world runs, because every live frame holds absolute pointers into it in saved registers. Moving it would leave every frame below the current one pointing into freed memory. But its size can be chosen when the world is built: `slas-rv32 --rootstack BYTES` writes it into the world block, and the glue starts the runtime with it.

A smaller root stack was not safe, though. Compiled code pushes a frame by adding to the stack pointer and never checks the end (chapter 6). The glue kept a canary in the stack's last word. That caught a recursive test world at depth 200 in 4 KB with "root stack overflow". At depth 1,000 the world had already run far past the end, trampled its own heap, and died of a type error.

So the rv32 backend now checks every push. Before, the push was a generic 64-bit add of nine instructions on a 32-bit machine. Now it is five: add, load the end through the table, compare, and branch past a call to a fatal `rt_rootstack_overflow`. The check therefore costs less than the code it replaces. The runtime's unit has 454 bytes less code. A world's own module changes by −16 to +232 bytes, and every call got faster: flaky's ping by 40 instructions, a snake tick by 740. SLIR does not change.

There is one wrinkle. A function's prologue zeroes a frame's slots before it pushes the frame, so a push that fails the check has already written up to a frame's size past the end. The embedder keeps 1 KB allocated past the checked end, and slas-rv32 refuses any frame bigger than that. The largest frame in all 287 programs and worlds is 496 bytes, agenda's. Zeroing after the push would remove the slack, but that changes SLIR, so it is left as an exercise.

The default is now 4 KB, ten times the most any test world used. A small world's blocks fall from 99 KB to 38.7 KB, and flaky as a unit takes 48 KB of its 320 KB. A world that needs more is built with `--rootstack`. The recursive test world fits 160 levels in 4 KB. At 170, 200, 1,000 and 100,000 levels it crashes at once with "root stack overflow" and sends no reply.

## 30.11 Testing

- `sh tools/rv32/nw-test.sh`: for each world in tests/native, build its module, load it on the emulator into the fake-kernel firmware, send its events, and require the calls in tests/native/NAME.out, which the host build makes. The run ends with the C module built the board's way. Modes: with a snapshot (the default), `NOSNAP=1`, `UNITS=1`, and `UNITS=1 MULTI=1`, which also runs the no-swap control and requires it to fail.
- `node run-tests.js --rv32`: every program of the suite on the emulator (chapter 29), with every push checked.
- `node run-tests.js` and `node tools/slir-compare.mjs`: unchanged SLIR for every program. Nothing in this chapter changes SLIR.
- The host's `tools/nw-fake-test.sh` (JIT, AOT, SHARE) and `tools/nw-multi-test.sh`, after the fake kernel's printing functions moved to a file that both kernels share. The lines are the host's by construction.
- Merging this work found two faults. Main's rv32 test firmware had not built since chapter 33's stage-1 natives, which needed stdio functions its small C library lacks. And `run-tests --rv32` wrote each program's object into the firmware's own build folder, where the object of tests/exceptions/runtime.js replaced the firmware's runtime.o. The next firmware link then failed, with a floating-point ABI mismatch and missing symbols. Programs now go to a folder of their own.

## 30.12 Against the real project

**Sizes.** The six worlds of chapter 24, as modules, in bytes loaded, which is what `mem_kb` is charged for the module:

| world | alone | alone, snapshot | unit, snapshot | own code as a unit |
|---|---|---|---|---|
| flaky | 170,888 | 88,480 | 10,528 | 3,990 |
| keyboard | 223,088 | 147,696 | 27,768 | 15,898 |
| power | 232,040 | 156,152 | 36,472 | 27,352 |
| keys | 200,992 | 138,176 | 38,968 | 25,606 |
| snake | 243,360 | 176,512 | 82,560 | 58,428 |
| repl | 205,848 | 144,216 | 47,952 | 35,118 |

rv32 code is 1.7 to 1.9 times the size of the same worlds' x86-64 code, because a 64-bit word on a 32-bit core takes several instructions. For a world built as a unit, the dynamic tables are a third of what loads (3,660 of flaky's 10,528 bytes). They could stay out of the loaded block if elf_loader reads them from the file, which is one more assumption to check.

**Time.** Instructions per call, as units with snapshots:

| world | init | a typical event |
|---|---|---|
| flaky | 35,163 (49,740 alone, without a snapshot) | a ping: 15,776 |
| snake | 180,668 (320,144 alone, without a snapshot) | a tick: about 543,000 |

At 400 MHz and one instruction per cycle, a snake tick would be about 1.4 ms and flaky's ping 40 µs. Code running from PSRAM through a 16 KB instruction cache will not always get one instruction per cycle. The board's own measurement is still to be made.

**What picocalc-os would change**, in its own code, which this chapter does not touch:

- search `cji_resolve[]` after its own names in `resolve()`, and link the runtime, the glue and the runtime's unit into the firmware;
- give the module's table a way to say "crashed", so that a crashed world is reported as one rather than as a broken protocol.

The memory charge needs no change on its side. Every assumption in §30.6 still needs checking against elf_loader 2.0.0's source, or by a run on the board.

**What comes next.** Worlds compiled on the host now load on the board's terms. The next step is chapter 33's compiler on the same terms: stage 1 assembled for rv32, slas in the firmware writing code into executable PSRAM, and a world compiled on the emulated board equal to the host's. That is the last phase of compiling on the device.

## Exercises

1. A unit-built module's dynamic tables are a third of its loaded bytes. Move `.dynsym`, `.dynstr`, `.hash` and `.rela.dyn` out of the first loadable segment, so that only the file holds them, and say which assumption about elf_loader that rests on. What does flaky then load?
2. The prologue zeroes a frame's slots before the push, which is why the root stack keeps 1 KB of slack. Zero them after the push instead, measure the SLIR and code-size change, and remove the slack.
3. The snapshot block is copied into the heap when a world starts, so its words are paid for twice. Let the heap start with the snapshot's block in place (chapter 27, exercise 1), and measure flaky's and snake's blocks.
4. Add a third function to the module's table that returns why a world crashed, write the change picocalc-os's kernel would need to report it, and make the fake kernel report it.
5. The glue swaps a world's state on every call, even when only one compiled world is loaded. Measure the swap's share of flaky's ping, and make it free when the world in the runtime is already the one being called.
6. elf_loader 2.1 resolves a named relocation to the module's own definition when there is one. Under that assumption, which `R_RISCV_RELATIVE` words could become named, and would anything get smaller?

## In SPJ

SPJ's design names three places a compiler could run (chapter 32): ahead of time on the build host, with modules bundled into the firmware; on the P4 when a world starts; and in a browser. This chapter serves the first two without bundling anything per world. A world compiled anywhere becomes the module picocalc-os's native worlds already use, loaded by elf_loader when the world starts and talking to the kernel through two tables. The runtime sits in the firmware once, and the world brings only its own code.

picocalc-os's native-worlds design was written for C. Its kernel table, its charging allocator and its crash on a broken protocol all assume a module whose author controls every allocation and every exit. A cji world has a runtime under it that allocates on the world's behalf and stops on fatal errors. Routing both through the world's own module, rather than changing the kernel, keeps the contract as it is. That is what lets a compiled world and a C world sit on the board side by side, loaded and charged the same way.
