# 24 · The Engine in the PicoCalc Host

Chapter 23 ran each world against a model of picocalc-os's kernel. This chapter runs compiled worlds inside picocalc-os itself. The kernel, the compositor, the other worlds and the simulated board are all real, and the results are compared with picocalc-os's own screenshots under QuickJS. It is the first chapter of the road to the device, and the choice it makes decides the rest: a compiled world talks to the kernel through the *native-world interface*. On the Linux host a native world is a process under seccomp. On the ESP32-P4 it is an ELF module. The calls are the same. A world that works through the interface on the host needs only code for a different processor on the device.

The result: six worlds (flaky, keys, snake, repl and the keyboard and power drivers) run compiled. 61 of picocalc-os's 72 screenshots are byte-identical to the QuickJS build's. The other eleven differ in the clock's accounting and in the text of a crash, and §24.7 explains both. The chapter also finds the next problem: a compiled world needs about 3 MB, where QuickJS gives these worlds 320 KB (repl 384).

## 24.1 The grammar

Nothing new for programs. The runtime of this chapter is written in the subset and uses four operations that no world can name. Like chapter 16's `$arity` and `$drain`, they are intrinsics that the runtime's loader turns into Prims:

| intrinsic | Prim | does |
|---|---|---|
| `$hostArg(k, v)` | `host_arg` | sets argument k of the next system call: a string (k = 0, 1, 2), the number c (k = 3), bytes (k = 4) |
| `$hostCall(op, a, b)` | `host_call` | makes system call op; its text, or its number when it has none (op −1: why the last one failed) |
| `$hostEvent(i)` | `host_event` | field i of the event being handled |
| `$hostEntries(init, event)` | `host_entries` | hands the runtime the two closures the kernel will call |

## 24.2 What picocalc-os does

picocalc-os runs every driver, service and app as a *world*. A world is normally a QuickJS runtime that evaluates the prelude and then the world's file. A world whose manifest entry says `"engine": "native"` is instead a binary that defines two functions, `nw_init` and `nw_on_event`, and calls the kernel through the `nw_*` functions of picocalc-os's sdk/nw.h. Every call acts for the calling world only, with that world's claims, exactly like the JavaScript operation of the same name.

The calls, numbered as sdk/nw_wire.h numbers them:

| op | call | op | call | op | call |
|---|---|---|---|---|---|
| 1 | log | 8 | need | 15 | i2c (a token) |
| 2 | now (µs since boot) | 9 | provide | 16 | release |
| 3 | self | 10 | every (a timer) | 17 | store load |
| 4 | send | 11 | kind | 18 | store save |
| 5 | publish | 12 | ask (a token) | 19 | timer on/off |
| 6 | reply | 13 | sleep (a token) | 20 | screen |
| 7 | reject | 14 | i2c open (a handle) | 21 | present (title, icon, about, key) |

And the events: a message (`NW_MESSAGE`, possibly an ask), a tick of a timer (`NW_TICK`), the start turn (`NW_START`), and the settling of a token (`NW_SETTLE`, ok or failed, with JSON). An asynchronous call returns a token at once, and its result arrives later as a settle event with that token. `nw_on_event` returns `NW_DONE` when the turn is over, or `NW_LATER` when it will answer an ask in a later event.

On the host (host/native_proc.c) the binary is run from memory as a child process. It must be statically linked. Its only way out is descriptor 3, a socket, and a seccomp filter kills it if it tries anything else. The kernel also limits its memory to the manifest's `mem_kb`. On a board (sdk/nw_elf.h) the binary is an ELF module that Espressif's loader relocates into memory. The kernel calls its `init` and `event` through a table, and the module calls the kernel through another. The `nw_*` functions are the same in both, which is what makes this route the device's route too.

The interface carries only those 21 calls. The prelude's other operations, `sys.*`, files, SPI, framebuffers, the network and the clock's zone, have no call. A world that uses them cannot run through the interface. So the compositor, display, about, sysmon, launcher, files, loader, settings and agent stay on QuickJS for now.

## 24.3 The interpreter

Only a world inside picocalc-os has a kernel to call, so the interpreters stop at a host call. An embedder that wants to run the native runtime in the interpreters can give them a kernel:

```js
let HOST = null;
export function setHost(h) { HOST = h; }
const hostOp = (op, args) => {
  if (!HOST) throw new Trap('host calls run only in a world inside picocalc-os');
  return HOST[op](...args);
};
```

`host_entries` is the exception: it only stores two values, so the interpreters accept it and do nothing. The model does the same.

## 24.4 The native world runtime

src/world-native.js is the world runtime of chapter 16, rewritten for a real kernel. The builder, the ui vocabulary, `show` and `errText` are chapter 23's. What changes is everything that reaches outside the world. Each such operation is now one system call:

```js
function $call(op /*: Int */, a /*: Int */, b /*: Int */, s0 /*: Any */, s1 /*: Any */, s2 /*: Any */) /*: Any */ {
  $hostArg(0, s0); $hostArg(1, s1); $hostArg(2, s2);
  return $hostCall(op, a, b);
}
function send(to /*: Any */, type /*: Any */, payload /*: Any */) { $check($call(4, 0, 0, to, type, $json(payload))); }
function now() /*: Any */ { return $call(2, 0, 0, undefined, undefined, undefined) / 1000; }
```

An asynchronous call becomes a promise whose resolvers wait in `$pending` under the call's token:

```js
function $later(token /*: Any */, resolve /*: Any */, reject /*: Any */) {
  if (token < 0) { reject(new Error(String($hostCall(-1, 0, 0)))); return; }
  const n = $pending.length;
  $pending.length = n + 1;
  $pending[n] = { token: token, resolve: resolve, reject: reject };
}
function sleep(ms /*: Any */) /*: Any */ {
  return new Promise((resolve /*: Any */, reject /*: Any */) => $later($call(13, ms, 0, undefined, undefined, undefined), resolve, reject));
}
```

A settle event finds the token, removes it, and resolves the promise with the JSON result, or rejects it. The kernel's two entries do what the prelude's `__init` and `__dispatch` do. `$nwInit` declares the world: its kind, title, icon, about and key, the channels it needs and provides, and its timers. `$nwEvent` handles one event and then sends the screen:

```js
function $nwEvent() /*: Int */ {
  let later = 0;
  try {
    Math.$clock($BOOT + now());
    const kind /*: Any */ = $hostEvent(0);
    if (kind === 0) later = $message();
    else if (kind === 1) $tick($hostEvent(5));
    else if (kind === 2) { if ($def.start !== undefined) { … $call3($def.start, $S, undefined, { from: '', type: 'start', ask: false }) … } }
    else if (kind === 4) $settle();
    $drain();
    $render();
  } catch (e) { $crash(e); }
  return $crashed ? 2 : later;
}
```

A message whose handler returns a promise is answered when the promise settles: `nw_reply` with its JSON, or `nw_reject` with the error's text. `$message` returns 1, `NW_LATER`, for an ask still unanswered. A handler that throws crashes the world, as it does under QuickJS: the runtime logs the error and the entry returns 2, which tells the bridge to exit. The wall clock is the prelude's when the kernel has none, BOOT plus `now()`. `Math.random` is seeded as the kernel seeds the prelude's: the low 32 bits of the FNV-1a hash of the world's name. The bridge computes that hash in C and passes it as event field 7.

The world's file runs in the program's `main`. The program then ends with one more statement, which the loader adds:

```js
$hostEntries($nwInit, $nwEvent);
```

§24.5.2 explains why the entries must be handed over as values.

## 24.5 The passes and the runtime

### 24.5.1 Four operations

The four Prims pass through the compiler like chapter 19's dynamic operations. They appear in `STRING_SOURCE_ARITY` and `STRING_ARITY` (the grammar checks); `host_call` and `host_event` are in `STRING_ALLOC`, because their results are new strings. Inference, type_check and local-types give `host_arg` and `host_entries` the type Int and the other two Any. cast_insert casts the numbers to Int and the values to Any. Instruction selection needs nothing new: an operation in `STRING_ARITY` becomes a call of the runtime function of the same name, with the root stack's top when it allocates.

In the runtime, `host_arg` copies a string into a buffer as UTF-8, so the kernel never sees the heap. `host_call` passes the three buffers and the numbers to the kernel's `call`, which the embedder installs as `rt_kernel_call`, and turns a text result back from UTF-8 into a string:

```c
int64_t rt_host_call(int64_t op, int64_t a, int64_t b, int64_t *roots)
{
	static char out[HOST_STR_MAX + 1];
	int64_t r;
	if (!rt_kernel_call)
		type_error("host calls run only in a world inside picocalc-os");
	out[0] = '\0';
	if (op == -1)
		r = rt_kernel_error ? rt_kernel_error(out, sizeof out) : 0;
	else
		r = rt_kernel_call((int)op, (int)a, (int)b, host_c, host_set[0] ? host_s[0] : NULL, host_n[0],
			host_set[1] ? host_s[1] : NULL, host_n[1], host_set[2] ? host_s[2] : NULL, host_n[2], out, sizeof out);
	…
	if ((op == -1 || r >= 0) && out[0])
		return string_of_utf8(out, strlen(out), roots);
	return from_double((double)r);
}
```

### 24.5.2 Calling compiled code from C

Until now only slas called compiled code, and only once: `main`. A native world is called by the kernel, once to start and once per event, long after `main` has returned. Three things had to change, and each was found by a crash.

**The root stack.** A compiled function finds the root stack's top in register s0, and only `main` loads it, from `rootstack_begin`. An entry is called when no compiled frame is live, so it starts the root stack the same way. The rule in src/prelude.js now reads `f.name === 'main' || f.name.startsWith('$nw')`.

**The calling convention.** Compiled functions use SLJIT's register-argument convention, which C cannot call. slas gives an entry a C entry of one argument, the closure, and moves it to R0, where every compiled function finds its closure:

```c
	if (!strcmp(fn->name, "main") || !strncmp(fn->name, "$nw", 3)) {
		…
		int entry = strncmp(fn->name, "main", 5) != 0;
		sljit_emit_enter(C, 0, arg_types(entry ? 1 : 0, 1), fn->scratches | SLJIT_ENTER_FLOAT(2), fn->saveds, fn->local);
		if (entry)
			sljit_emit_op1(C, SLJIT_MOV, SLJIT_R0, 0, SLJIT_S0, 0);
	}
```

**The closure.** The first version called `$nwInit` with no closure and crashed at its fourth instruction: `mov r6, [s0-32]; mov [s0-24], [r6+88]`, a load from the closure. The world's top-level variables are `main`'s locals, and a top-level function that uses them is a closure over their boxes. Its closure is made when `main` runs, and nothing outside `main` holds it. So the program hands both closures to the runtime (`host_entries`), which keeps them in `rt_entries`. The collector treats them as roots and updates them when it moves them, as it does `exc_value`.

### 24.5.3 slas as a library

slas's `main` became three functions: `slas_load(f, verbose, code_out)` assembles a program read from a stream, `slas_function(name)` finds a function's code, and the command line is what remains of `main` (left out with `-DSLAS_LIBRARY`). `slas_function` looks for the exact name first and only then for a numbered one (`$nwEvent.54`). The first version took the numbered form first, and five async tests whose programs define a function called `main` found that function instead of the program's entry.

slas's tables were fixed arrays sized for the largest program: 65,536 calls, 4096 labels, functions and closures. In a world binary they came to 7.8 MB of bss, which the kernel's memory limit counts in full. Every table now grows as it fills (`grow`, doubling from 64), and the bss is 1.3 MB.

### 24.5.4 The bridge

runtime/nw_world.c is both sides of the interface for a compiled world. `nw_init` installs the kernel calls, assembles the world's SLIR, which is built into the binary as bytes, from memory (`fmemopen`), runs `main`, and calls the init entry with its closure:

```c
void nw_init(void)
{
	…
	rt_kernel_call = kernel_call;
	rt_kernel_error = kernel_error;
	nw_self(name, sizeof name);
	rt_event.seed = (double)(fnv(name) & 0xffffffffu);
	f = fmemopen((void *)cji_world_slir, cji_world_slir_len, "r");
	if (!f || slas_load(f, 0, NULL))
		fail("cji: the world's code could not be assembled");
	fclose(f);
	rt_initialize(CJI_HEAP_BYTES, 1 << 16);
	…
	if (main_fn() != 0 || exc_flag)
		fail("cji: the world's file stopped with an exception");
	if (init(rt_entries[0]) == 2)
		_exit(4);
}
```

`nw_on_event` copies the event to `rt_event`, where `host_event` reads it, and calls the event entry. `kernel_call` maps each operation number to its `nw_*` function. These are the functions sdk/nw_proc.c provides in a process and sdk/nw_elf.c provides in an ELF module.

### 24.5.5 Building a world

`node tools/nw-build.mjs world.js out` compiles the world with the native runtime (`cji.js --native --emit`) and writes its SLIR as a C array. It then links that statically with slas, the runtime, SLJIT, the bridge and picocalc-os's sdk/nw_proc.c. flaky's binary is 1865 KB, of which 417 KB is SLIR; snake's is 1992 KB.

## 24.6 Testing

A native world is hard to debug inside the kernel's sandbox: its standard output goes nowhere, and a fault is reported only as "segmentation fault". tools/nw_fake.c is a fake kernel. Its `nw_*` functions print what they are given, and its `main` sends the events named on the command line. Linked with the same objects, a world runs under gdb like any program. tools/nw-fake-test.sh builds each world named in tests/native/*.events and compares the calls it makes with the recorded ones. For flaky:

```
kind service
-> done
reply "pong 1"
-> done
reply "pong 2"
-> done
sleep 50 -> token 1
-> later
reply "finally done"
-> done
reject flaky has no handler for "missing"
-> done
log crashed: boom, thrown on purpose
```

tests/tail/nulllen.js checks the one language change this chapter needed. `.length` of `undefined` is a TypeError that `try` catches, where it was a trap. Snake's screen reads `s.body.length`, and the first version of the runtime rendered the screen before the start turn had made `s.body`.

## 24.7 Against the real project

tools/picocalc-shots.sh does what SPJ's integration does. It builds the named worlds, copies picocalc-os's manifest with those worlds marked native, runs every one of picocalc-os's twelve host scripts in a fresh root with the unmodified host, and compares each capture with the QuickJS build's.

| worlds compiled | captures identical to QuickJS |
|---|---|
| flaky | 67 of 72 |
| flaky, keys, snake, repl, keyboard, power | 61 of 72 |

The eleven that differ fall into two kinds.

**Accounting.** The kernel charges a native world's turn by its process's real time, and a QuickJS world's by its virtual steps. So with compiled worlds in the system, the shared virtual clock reads a little differently. Every screen that shows a time, a tick count or a world's statistics differs slightly. The REPL's `now()` reads 16044.182 where QuickJS's reads 16035.55. Snake's later capture shows the same game, the same food and the same autopilot moves, one tick further on. The keys app shows event times, and about and sysmon show every world's turns and memory. SPJ's in-process integration has the same kind of difference ("only in the virtual clock's and the heap's accounting"). Native worlds also always receive a start turn, which QuickJS worlds get only when they declare `onStart`, so turn counts differ too.

**A crash's text.** When flaky throws, the kernel reports "flaky crashed handling boom: boom, thrown on purpose (system/flaky.js:4:38)" for QuickJS, and "it exited with status 4" for the compiled world, because a process can only exit. The faults app shows that line. The world logs the error itself before it exits, but the kernel's report is what the screen shows.

**Memory.** The comparison above gives the compiled worlds 16 MB. With 3 MB all six still run; with 2 MB snake runs out. QuickJS gives these worlds 320 KB (repl 384). A compiled world carries its SLIR text, an assembler and the assembler's working memory, and every function of the prelude and the library whether it is used or not. That is the subject of the next chapter.

## Exercises

1. `$nwEvent` sends the screen after every event, and the kernel compares it with the last one. Send it only when the state could have changed: after a message, a tick or a start, not after a settle that resolved nothing. How many `screen` calls does keys.txt save?
2. Give the native runtime `hw.fs` through an extension of the interface: one new call, numbered 22, carrying an operation name and JSON arguments. Write the kernel's side as a patch to nucleus/native.c, and say which of picocalc-os's worlds it would let run compiled.
3. The crash text: make the runtime pass the error's text to the kernel before it exits. Which call of the interface could carry it, and what would the kernel need to show it as QuickJS's?
4. A payload of JSON `null` arrives as `undefined` in the native runtime. Find a world for which this matters, or argue that none can.
5. Measure the time from the kernel's start of a world to its first screen, for QuickJS and for the compiled world. How much of the compiled world's is assembling its SLIR?

## In SPJ

SPJ took the other road. Its integration (protojs `integrations/picocalc/spj_backend.c`) compiles a world when it loads, inside the host process, and runs it in its own SPJ context: its own heap, job queue and world definition. It implements the prelude's operations by calling the kernel's internals directly. The `sys.*` operations, files, the clock and the network are all there, so fifteen worlds run compiled. The backend says plainly where it goes around the native interface ("NOT IN THE NATIVE ABI"), for the start turn and for the screen's size limit. That road needs a backend compiled into picocalc-os, on the host and on the board. This chapter's road needs nothing from picocalc-os that it does not already offer, and so it reaches fewer worlds until the interface grows.
