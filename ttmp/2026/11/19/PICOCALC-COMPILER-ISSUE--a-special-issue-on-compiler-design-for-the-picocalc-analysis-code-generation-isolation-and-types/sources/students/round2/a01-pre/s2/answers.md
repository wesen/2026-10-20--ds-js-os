# Answers

1. On a machine this small the device has to stay responsive to input, timers and other worlds, so no world may hold the CPU for the whole duration of its computation. Also, a fault or runaway loop in one world must not be able to freeze the whole machine, which is only possible if control returns to a supervisor regularly. So instead of running a loop to completion, a world runs it in steps (a slice, or a budget of instructions or allocations) and then yields a message back to the scheduler, which resumes it later. The loop therefore becomes a resumable state machine rather than one blocking call.
Confidence: 3

2. I cannot know this without the article, since it never appears here which three engines are meant. My best reasoning is that they would be something like (a) a byte-code or tree interpreter over untyped values, (b) a typed/native compiled engine, and (c) a WebAssembly engine, and that the split exists precisely because they differ in isolation strength. Typically the interpreted engine is fully memory-safe and cannot damage other worlds, the WebAssembly engine is sandboxed behind a linear-memory boundary and also cannot (barring host bugs), and a native compiled engine runs raw machine code in the shared address space, so a wild pointer or bad jump there can corrupt the supervisor or any other world. A fault in the program under the native engine is therefore the one that can damage other worlds.
Confidence: 2

3. I cannot know this without the article, but the two facts would have to be things the function text does not state. First, the concrete representation of the values crossing the boundary: the width, signedness, layout and pointer-vs-integer status of `countUnit`'s parameters and result, which must be read off the declarations or the call sites. Second, the calling convention the callers expect: argument order, who cleans up, where the return value lands, and which globals or statics the function touches, which is only knowable from the rest of the program. Root/ownership information for anything the function stores would plausibly be a third such fact.

4. I cannot know this without the article, but the size gap is the kind of thing a static-vs-hosted runtime split produces. The native Editor most plausibly carries more of its own machinery into the image: its own allocator, its own copies of runtime and library code, alignment and page padding, and possibly more than one engine, none of which can be shared with a host that already has them. The WebAssembly Editor can lean on the host runtime, share library code and use a compact module format, so its footprint is only the delta it adds. Another candidate reason given in such articles is that the native build keeps both the interpreter and the compiled path resident while the WebAssembly build relies on the host's compiler.
Confidence: 2

5. I cannot know this without the article's exact naming, but the shape has to be the same as any other service on this machine. The application world never touches the LCD: it sends a message describing the operation (draw this text at this position with this style) to the world that owns the display. That display world receives the message on its queue, updates its own framebuffer state, and only it performs the final transfer to the LCD hardware. So the path is application world → message → display/desktop world → own framebuffer → hardware push, with each hop crossing an isolation boundary rather than a shared pointer.
Confidence: 2

6. I cannot know this without the article, but "hybrid" in this setting almost certainly means a world that is part code and part data: some of what it does is host-side or shell-provided code, while the rest is data and programs kept in the store, so it does not have a single uniform language or a single uniform execution mode. Because of that, their row in the compile-time table is not the same kind of measurement as Editor's. Editor is one known program built from a known set of sources, whereas a hybrid's row combines prebuilt host code with user-supplied content that is compiled or interpreted later, on demand, so the timing covers different work per unit and cannot be compared line by line with Editor's.
Confidence: 2
