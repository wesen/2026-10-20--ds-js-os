# Answers to "9. Types That Pay for Themselves"

1. I cannot know this without the article, since section 9.2 names specific places in their sources. My best reasoning about what the answer must look like: the three sites are almost certainly places where an `Int` stands in for a small closed set of cases — candidates are token or AST node tags, bytecode opcodes, or a discriminant for "which of several buffers, panes or modes" the editor is in. Replacing such an integer by an enumeration would not change the generated machine code much, because enum tags still compile to integer discriminants; what changes is that a `switch` over the enum becomes exhaustive, so codegen can drop the `default` arm and the unreachable-tag error branch, and the checker rejects a wrong tag at the call site rather than at runtime.
Confidence: 2

2. I cannot know this without the article, so I will reason about the shape the answer must have. Four coordinate systems for one position in an editor usually means something like: a byte offset into the raw text, a (line, byte-column) pair into the line table, a visual screen column that accounts for tabs and wide glyphs, and a grapheme-cluster or codepoint index used for cursor motion. The mistake such tests tend to miss is a conversion that happens to be the identity on the test data — plain ASCII, no tabs, no wide characters, no mixed line endings — so two systems agree numerically and a wrong conversion passes, failing only on tabs, emoji, combining marks, CRLF, or a position exactly at a line end.
Confidence: 2

3. I cannot know the exact loop of section 9.4, but the structure described is a flow-sensitive fact the compiler holds for a region of straight-line code, something like "this index is inside this buffer" or "this pointer is non-null", established by a test and reused by later operations. The three kinds of discarding event are the standard ones: a write that could change the tested value or anything it depends on, a call whose effects are unknown so anything might have changed, and a control-flow join — a branch merge or the loop back-edge — where the fact may hold on one incoming path and not another. Nothing must be remembered across iterations because the fact is not loop-carried: it is re-established by the test at the top of each iteration, so it only covers the body and dies at the back-edge, which is why the analysis never has to iterate to a fixed point to find facts that survive a full turn around the loop.
Confidence: 3

4. A signed test `at < text.length` rules out only the upper side of the interval, because a signed `at` may still be negative, and a negative index that passes the test is exactly the out-of-bounds read the check exists to prevent. So the check can be narrowed but not removed: you still need the lower bound, either as a separate `at >= 0` or folded into a range test, and it is the sign test, not the whole check, that the compiler may then drop. An unsigned index type removes the lower half of the problem by construction, since negative values are not representable, so a single comparison suffices with no risk of a wrapped or negative index slipping through. The trade is that subtraction near zero now wraps, so the unsigned type only pays off when lengths and indices are unsigned together.
Confidence: 4

5. The two rules that make a per-turn arena safe are, as I would state them: memory is freed only wholesale at the turn boundary and never piecewise, and no reference into the arena may be stored anywhere that can outlive the turn. The second rule is what makes the first safe, because the arena is dropped without asking anyone, so a dangling reference would show up with no failing call to blame. A program holding data that must survive the turn therefore has to copy it out explicitly, into storage that outlives the arena, before the turn ends.
Confidence: 3

6. At the end of each branch the grant must have been consumed exactly once — spent on a real operation or explicitly released — so that no live grant remains at the join; a linear type admits no other ending. The two branches may dispose of it in different ways, provided each disposal is a legal consuming operation, because linearity constrains how many times a value is used, not which operation consumes it. What they may not do is leave one path holding a live grant while the other has released it, since the join point would then have to carry two different statuses for the same variable. The payoff is that "the permission was revoked on every path" becomes something the checker proves instead of something a comment promises.
Confidence: 4
