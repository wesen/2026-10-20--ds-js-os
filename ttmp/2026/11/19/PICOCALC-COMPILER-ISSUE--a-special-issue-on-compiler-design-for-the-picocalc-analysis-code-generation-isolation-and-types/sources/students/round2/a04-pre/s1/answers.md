# Answers

1. A jump function is the abstract-transfer version of an expression: it maps incoming ranges for the variables in `e` to the range of `e` itself, and for "add a constant" it is just a shift. So for the first argument of `clamp`, which I take to be `i + 1`, the jump function is `J(i+1, [a,b]) = [a+1, b+1]` (with a wraparound case to split if the type is fixed-width and the interval crosses the maximum), and for `i` in `[5,7]` the argument's range is `[6,8]`. The bounds `clamp` itself supplies can only narrow that interval, never widen it. If the first argument is instead something like `i - 1`, the same rule gives `[4,6]`; I cannot confirm the body of `nextIndex` without the article.
Confidence: 3

2. The reasoning confuses a *fact* with a *function of the calling context*. A summary is not "the result is always X"; it is a jump function from the callee's input ranges (and relevant global/object state) to its output ranges, plus its effects, so a changed caller simply re-instantiates the summary at the new argument ranges and still gets a correct, often tight, answer. The change that really invalidates a memoized summary is a change to the *callee* body (or to state it reads), which is a different event from a caller changing. So "callers keep changing" is an argument for parameterising summaries, not against computing them once.
Confidence: 4

3. In plain SSA the two definitions of `i` meet at a phi node, after which a single name denotes either value, and the guard `i < n` is no longer recorded anywhere on that name. A range analysis therefore has to join the two incoming ranges (often widening to the whole type range or to `[MIN, n]`), so it loses exactly the refinement the branch provided, and also cannot recover which use is dominated by which condition cheaply. Extended forms add condition-tagged renamings — gated SSA (GSA) with gates, or sigma/pi nodes as in SSI — so the "true" and "false" versions of `i` stay distinct and each use carries the predicate under which its value holds, which is what makes precise path-sensitive range propagation expressible in a single pass.
Confidence: 4

5. "Local checking" means checking one function's body using only the ranges and types of its own parameters (plus whatever is locally visible), rather than needing facts about all its callers — i.e. verification is compositional and per-unit. Two practical consequences on a handheld: first, compile time and memory stay bounded and predictable, because there is no whole-program fixed point to iterate and no giant call graph to hold in RAM; second, results become order-independent and cacheable, so a function can be checked once, stored, and reused, and incremental rebuilds only re-check what changed. The price is that anything the caller knows but the parameter types do not record is thrown away at the boundary.
Confidence: 4
