
### Where I would place the bets

| Priority | Research question | Why I would fund it |
|---|---|---|
| 1 · Best prospect for faster cold builds | What does it cost to turn typed source into operations on the P4, and how much of that work can disappear? | About 1.4 seconds of a roughly 2.45-second Editor build lies in an interval containing frontend work and setup. If we could halve that interval while leaving everything else fixed, Editor would compile in about 1.75 seconds, a 29% reduction. That is a sensitivity calculation, not a forecast. It tells us where an ambitious experiment is justified. |
| 2 · Strongest candidate for original research | How much information should a streaming compiler retain about each function, and when does retaining it pay for itself? | We have two measured extremes. Streaming released about 358 KB of Editor compiler heap in the production comparison. A narrow static proof removed zero Editor bounds checks. Between those extremes is a real design question: can a small, explicitly bounded record of types, branch conditions, or value lifetimes buy enough better code to justify the time and memory spent constructing it? |
| 3 · Strongest engineering payoff with a clear finish line | Can Scope A make the generated program small enough to reduce Editor’s reserved native-code slot? | The combined candidate emits 82,028 instruction bytes. The proposed slot is 81,920 bytes before headers and entry points. The roadmap’s eventual slot reduction would free 144 KiB from the running Editor world and shrink its module by 61%. That is a meaningful device outcome even if cold compilation barely changes. |
| 4 · Best separate bet for the developer experience | After editing one function, how little must the compiler rebuild? | A whole-module cache helps when nothing changed. A function-level compiler could reuse unaffected functions after a real edit. The decisive experiment is to change a function body, a signature, and a shared record layout, then compare each rebuild against a clean compile. I’d give this its own edit-to-run metric so a fast cache hit can’t hide a slow cold build. |

### Where the novelty could be

Single-pass lowering, keeping operands in registers, and copying prebuilt instruction sequences all have substantial prior art. Implementing them gives us credible baselines and can improve the product. The research opportunity I find most persuasive is to predict, before compiling a function, how much analysis that function deserves under a fixed time and memory budget. V8’s Liftoff design · Titzer’s empirical study of baseline compilers · Xu and Kjolstad on copy-and-patch compilation

For example, consider two functions. One compares a directory flag and returns. The other scans text in a loop with guarded indexing. Which facts would the compiler retain for each? What cheap observation would let it choose? Can it discard the facts at the end of the function? Compare three policies: retain nothing extra, always run the analysis, and select functions under a fixed budget. Give the selection rule an app it has never seen. If it predicts which analyses pay on that app, we have a result someone building a different compiler could use. If always choosing the simplest policy wins, we’ve established something valuable about the limits of analysis on these workloads. Three familiar apps are enough to begin that experiment. A broader scientific claim needs held-out programs.

### How I would distribute the workforce

I’d run three independent implementation researchers and one supervising experimentalist. The single board can serve all three if one person owns the measurement schedule and everyone else can progress on the host.

| Owner | First assignment | Deliverable that decides what happens next |
|---|---|---|
| Researcher 1 · Frontend performance | Break down the 1.4-second interval on the P4. The current lexer runs a regular expression with named captures and constructs a token object on every successful match. Compare it with a cursor-based scanner if the trace shows scanning or allocation is material. | A time breakdown that reconciles with the clean build, plus one controlled implementation comparison preserving diagnostics and output. Current lexer (picocalc-os/compiler/typed-wasm.js:53) |
| Researcher 2 · Native code generation | Take Files from the 738-instruction fusion candidate toward the professor’s 593-instruction model. Explain the difference per function, then predict Agenda’s result before running it. | A model that predicts a second app, or an account of which assumptions failed. Continue to Editor and slot reduction once the model earns that confidence. |
| Researcher 3 · Bounded analysis | Prototype the three analysis policies on one useful class of facts. Record analysis time, peak bytes, and which generated instructions or dynamic checks actually disappear. | A comparison on a held-out workload. Preserve the negative result if selective analysis costs more than it saves. |
| Supervisor · Independent measurement and review | Freeze the production control, reserve board windows, rotate candidate order, and independently replay the strongest result. Use cheaper Sol agents for isolated prototypes and an Astra reviewer for experimental design, confounders, and synthesis. | One comparable result table covering cold time, compiler peak heap, emitted bytes, and guest execution time. Give edit-to-run latency its own column when the incremental study starts. |

I’d start the incremental-compilation study when the first of those lanes finishes. I’d also keep await on the language-research roadmap. Editor’s existing Open and Find workflows make it an excellent future study of how little state must survive a suspension. It answers a different question from the one the lab most urgently needs answered today.

My call as lab director: give the next wave one ambitious performance target and one scientific test. Aim to remove half a second from a clean Editor compile while preserving the current peak-heap budget. In parallel, ask whether a compiler can predict where extra analysis pays on an unseen program. The first would materially improve the handheld. The second could teach us something that outlives this particular device.
