# Independent editor research diary

## Step 1. Design

Model `claude-opus-4-6` with high effort. Request SHA-256 `c7c4569da91f4717719f9932102abd449b2b3c0b225274c607602c3cc862c222`. [Dated study receipt](../various/opus/editor-design.json)

1. **Prompt context.** The prompt situates this in a PicoCalc / Wasm project (`picocalc-eg-wave`). The working directory is `/tmp/picocalc-eg-wave/empty`, not a git repo. The request is for a *design document*, not running code. The audience is an implementation team plus archive.

2. **Interpretation.** "Resumable text editor" means a cooperative-multitasking text editor where long operations (search) must yield. "Hand-written state machine" is the manual CPS transformation pattern. "Generated start/resume" is the compiler-automated equivalent (stackless coroutine lowering). The comparison is about the cost of automation vs hand-tuning at this scale.

3. **Inferred intent.** The project likely investigates whether a code generator for resumable Wasm guests is worth building, or whether the workloads are small enough that hand-written state machines dominate. The 64 KiB size suggests memory-constrained targets where frame bloat matters.

4. **What I did.** Designed a minimal-surface experiment: one function (byte search), one buffer size, three completion classes. Chose 512-byte budget to produce a non-trivial yield count (~128) for miss, exercising the yield path without making budget logic dominate. Specified the ABI so both approaches are interchangeable from the host's perspective.

5. **Why these measurements.** Compiler cost captures the one-time price of the generator. Guest work captures per-search runtime. Frame storage captures the per-search memory cost. These three axes are independent and together determine whether the generator is viable on a constrained device.

6. **What worked in the design.** Fixing the PRNG seed eliminates buffer-content variance. Using a byte-at-a-time scan isolates yield overhead from search-algorithm effects. Making the frame opaque to the host means the host driver code is identical for both approaches.

7. **What did not (and adjustments).** An earlier draft had the yield budget as a parameter. This introduces a confounding variable; I fixed it at 512 to keep the experiment at 12 cells. A future study can sweep budgets. I also considered `memmem`-style search but rejected it because a vectorised inner loop would mask yield-machinery cost.

8. **What I learned.** The live-variable set at the yield point is the key driver of frame size difference. For this simple function, GSR captures 5 locals (20 bytes + tag) vs HSM's 15 bytes — a 60 % overhead in frame storage. For functions with more complex control flow (multiple yield points, nested loops), the gap widens.

9. **Tricky parts.** (a) Ensuring `search_start` can itself return `Hit` or `Miss` without ever yielding (required for the early-hit case with offset < budget). The HSM pseudocode handles this by tail-calling `hsm_resume` from `hsm_start`. The GSR generator must emit equivalent logic. (b) Wasm `clock_gettime` is not available natively; the host must bracket calls externally. The measurement method section specifies host-side timing for this reason.

10. **Independent review notes.** A reviewer should verify: (a) the yield-count invariant arithmetic (65536 / 512 = 128 yields for a full scan; minus 1 because the first call starts at 0 and processes bytes 0–511 before the first yield); (b) that the `mem_eq` call is not elided by the compiler at `-O2` (the buffer must not be a compile-time constant); (c) that Wasm linear-memory watermark measurement accounts for stack usage inside the guest, not just the frame struct.

11. **Next steps for the implementation team.** (a) Implement HSM in C, compile to both native and Wasm32. (b) Implement the straight-line source and the generator (can be a simple Python script emitting C for this single function). (c) Write the host driver (native: direct call; Wasm: wasmtime or wasm3 embedding). (d) Run the 12-cell matrix, check failure criteria before analysing timing data.

12. **Review instructions.** Compare this design against the actual implementation before collecting data. Any deviation from the specified ABI, buffer size, budget, or seed invalidates cross-cell comparisons. The failure criteria are hard gates, not guidelines — a failing cell means the toolchain has a bug, not that the data is noisy.

13. **Technical detail: Wasm frame storage.** In the Wasm build, the frame struct lives in linear memory at a host-chosen address. The generator may also spill temporaries to the shadow stack (if using LLVM's `__stack_pointer` global). The frame-storage measurement must capture both: `sizeof(Frame)` for the explicit struct, plus `(stack_pointer_before - stack_pointer_after)` for implicit spills during `resume`. The HSM version should show zero implicit spills since all state is in the explicit struct.

## Step 2. Report

Model `claude-opus-4-6` with high effort. Request SHA-256 `2b22798b9a6862a691a7ad5f3c868247c8d455abdd610623fed48aac642e98fa`. [Dated study receipt](../various/opus/editor-report.json)

1. **Prompt context.** The working directory is `/tmp/picocalc-eg-wave/empty`, not a git repository. The prompt supplies an experiment design for resumable text editor search and a block of verified physical measurements from an implementation team. The measurements reference specific git revisions (`1357545`, `2e4fee1`, `7b321a9`), prespecified gate labels (G3, G4 from PICOCALC-NATIVE-NEXT), and two physical execution engines on PicoCalc P4 hardware. The request is for a standalone pedagogical report with investigation diary.

2. **Interpretation.** The original design proposed a synthetic 64 KiB buffer with controlled needle placement. The implementation team executed a richer variant: a full typed Editor application with 13 workflows, plus a targeted Find fixture using the same 65,536-byte buffer with 851 CRLF lines. The "manual" arm corresponds to HSM; the "await" arm corresponds to GSR. The measurements span compiler cost, runtime, binary size, frame storage, yield structure, and visual equivalence. I am to analyze the supplied measurements, not generate or simulate any data.

3. **Inferred intent.** The project is evaluating whether to adopt compiler-generated cooperative yields for the PicoCalc Editor, replacing hand-written continuations. The measurements are decision-grade: they include prespecified gates with pass/fail outcomes. The report serves both as a technical record and as pedagogical material for a new compiler engineer joining the team.

4. **What I did.** Parsed each measurement block, computed the relationships between arms, verified that the reported percentage changes match the raw numbers (e.g., 2,645,557 → 3,816,925 is indeed +44.28%), cross-referenced the prespecified gates against the data, and identified the single failing gate. Structured the report around the five measurement axes: compiler cost, artifact size, runtime, query timing, and frame storage. Added visual equivalence as a sixth axis since it was measured.

5. **Why this structure.** The original design organized measurements as compiler cost, guest work, and frame storage. The implementation team added artifact size and visual equivalence. I followed the original taxonomy but expanded it to cover all supplied data. I separated the workflow layer (13 integrated workflows, three trials) from the query layer (single-trial Find measurements) because they have different statistical properties and should not be conflated.

6. **What worked.** The prespecified gates provide a clean pass/fail framework. Four of five gates pass; the failing gate (compiler cost) is unambiguous and the magnitude (+44–54%) is far outside the 10% threshold. The segment and settlement counts provide exact yield-structure equivalence, which is a stronger signal than the timing data. The screenshot hash comparison provides pixel-level visual equivalence. These three signals — gate outcomes, yield counts, screenshot hashes — form a hierarchy from quantitative to structural to visual.

7. **What did not work or required care.** (a) The "us" field in the workflow data is labeled as "the compiler interval, not entire boot," which could be misread as Editor runtime. I verified from context that it refers to compilation time and separated it from `workflow_cpu_ms`. (b) The query-layer data is single-trial. I explicitly disclaimed statistical inference from these points and flagged the RV32 early-hit −9.83% as potentially noise. (c) The original design predicted GSR frames would be larger; the actual measurement shows them one word smaller. I reported this discrepancy rather than forcing the data to match the prediction.

8. **What I learned.** The generator's cost is concentrated in compilation, not runtime. This is consistent with the theoretical expectation: the continuation-passing transformation is a compile-time rewrite that produces equivalent code. The 0.76% Wasm binary size increase (667 bytes) is remarkably small, suggesting the generator's dispatch tables compile to nearly the same code as the hand-written switch statements. The identical segment counts across arms confirm that the yield-point placement is deterministic and matches between manual and generated versions.

9. **Tricky parts.** (a) The measurement notes state "Wall time sent to the app is fixed to show the identical clock in each raw screenshot, but all timers and timeout decisions still use the actual monotonic clock." This means the screenshots are comparable but the displayed timestamps are synthetic. I did not confuse displayed wall time with measured elapsed time. (b) "Delivered settlements" is the measurement's term for host-acknowledged yields; "Editor segments" is segments of Editor execution between yields. Segments = settlements + 1 for a completed search (the final segment returns the terminal status). I verified: 27 segments, 26 settlements — consistent. (c) The measurement cautions "Do not label injected events physical keypresses" and "Line number alone does not predict search cost; the SDK can skip a line in one seek." I honored both constraints in the report.

10. **Independent review.** (a) The prespecified gate `native_compile_within_10pct` fails at +44–54%, which is correctly reported as `False` in the supplied data. (b) The frame storage comparison (70 vs 71 words) favors the await arm by exactly one word, contradicting the original design's prediction of GSR being larger. This is a genuine finding, not a measurement error — the generator optimized away a redundant variable. (c) Module bytes being exactly identical on RV32 (240,452) across all six runs (three per arm) confirms deterministic compilation. The 667-byte Wasm difference is stable across all three trials per arm. (d) The workflow CPU medians (35.03 vs 34.80 ms on RV32; 144.35 vs 144.30 ms on Wasm) are within the measurement noise floor, confirming the runtime-parity hypothesis. (e) I verified that the Wasm/RV32 elapsed-time ratio for the miss query (1,762,060 / 183,880 ≈ 9.6× for manual; 1,656,603 / 171,667 ≈ 9.6× for await) is consistent, suggesting engine overhead scales proportionally.

11. **Predictions vs measurements.** The original design predicted: (i) GSR frame size would be larger — **contradicted**, it is one word smaller; (ii) yield counts would be deterministic — **confirmed**, segment counts are identical across arms and engines; (iii) runtime overhead of yield machinery would be measurable — **not confirmed**, differences are within noise; (iv) compiler cost would be higher for GSR — **confirmed**, and the magnitude (44–54%) substantially exceeds what a simple live-variable analysis pass would suggest, indicating the full transformation pipeline (analysis, dispatch generation, frame layout) is expensive.

12. **Next steps.** (a) Collect multiple trials for the query-layer measurements to enable statistical comparison. (b) Profile the compiler itself to determine which phases account for the 44–54% overhead — live-variable analysis, frame layout, or code emission. (c) Measure the on-target compilation path (RV32 self-hosting) to determine whether the compile-time overhead is tolerable for iterative development on the device. (d) Sweep the yield budget to characterize the relationship between segment count and per-segment overhead at different granularities.

13. **Review instructions for the implementation team.** Verify that revisions `1357545`, `2e4fee1`, and `7b321a9` are correctly identified as manual, await, and combined-port respectively. Confirm that the 13 Editor workflows exercised by the test harness cover all Find phases (E1–E7). Check that the 65,536-byte fixture buffer used for query timing is the same across both engines and both arms. If any query-layer measurement is repeated, update the report with the additional trials. The single failing gate (compiler cost) should be dispositioned by the project lead before the await transformation is adopted for production use.

14. **Technical detail: segment and settlement semantics.** A "segment" is one uninterrupted interval of Editor execution between entry (start or resume) and exit (yield or terminal return). A "settlement" is a host-acknowledged yield — the host received `Yield`, performed its scheduling duties, and re-entered the guest. For a search that yields N times, there are N settlements and N+1 segments. The terminal segment returns `Hit(offset)` or `Miss`. The early-hit case has 1 segment, 0 settlements: `search_start` returns `Hit` without yielding. This matches the original design's requirement that `search_start` can itself return a terminal status.

4. **Corrections incorporated.** (a) Both compiler intervals are measured on the real P4, not a development host. (c) The 13 Editor workflows are host semantic replays comparing the app to its JS reference; the physical short workflow is separate and compares two specific captured frames per trial, not every possible frame. The initial report incorrectly attributed the one-word reduction to the generator eliminating a redundant variable. (g) The 240,452-byte native module envelope is a fixed slot. Identical envelopes cannot prove identical native instructions; the actual programs differ at 21,922 vs 22,292 native words. (h) Single paired query measurements are exploratory; no universal performance estimate or per-yield noise threshold can be extracted. The initial report made overly broad claims from single trials. The measured compiler cost breakdown identifies dominant components without speculation. Presenting the query timing as a single table with all six cells, both elapsed and CPU, makes the exploratory nature transparent.

The initial report's strongest claim ("the transformation adds compile-time work that leaves no measurable residue in the artifact") was wrong: native code grew by 370 words, hidden by the fixed envelope. (b) Distinguishing host semantic replays (24 frozen, 13 with JS reference, 5 fixture) from physical short workflow (P4 hardware, two frames per trial) required careful re-reading of the measurement notes. (c) The compiler cost breakdown required restating the initial report's entire narrative. 7. **Compiler cost breakdown detail.** The 1,179.7 ms of added native compile time decomposes as 896.5 ms in the rewrite phase and approximately 283 ms elsewhere. Within the rewrite: 440.8 ms (37% of total added) reading input, 181.4 ms (15%) scanning for operations, 160.7 ms (14%) analyzing tasks, 57.1 ms (5%) building rewritten text. Reading and scanning together account for 52% of the added compile time. This profile suggests optimization should target I/O throughput before algorithmic complexity of the transformation.

8. **Query timing observations.** The elapsed clock includes scheduling between Editor segments; the CPU clock excludes it. For the rv32 late hit, elapsed time is 54.23 ms but CPU is 39.54 ms, with approximately 14.7 ms consumed by 26 scheduling boundaries. For the wasm late hit, elapsed is 732.41 ms with CPU of 604.11 ms. The late hit at line 852 does not require scanning every preceding byte because the SDK can skip a line in a single seek. The miss query produces 296 settlements and spends the most time in scheduling boundaries. All timing figures are exploratory single-trial measurements.

9. **Native word growth.** G3 added 264 native words to E6 control (21,922 to 22,186). G4 added 106 further (22,186 to 22,292). The total growth of 370 native words represents the generated dispatch, frame management, and control metadata. This is distinct from the fixed 240,452-byte envelope, which serves as a delivery container and cannot be used to infer instruction-level equivalence.

10. **Visual equivalence scope.** The physical short workflow compares two specific captured frames per trial, not every possible frame. The screenshot hash uniqueness (one hash per shot across all six runs per engine) confirms those specific frames are identical between arms. This is a necessary but not sufficient condition for full visual equivalence.

11. **Predictions vs measurements.** The original design predicted GSR frames would be larger due to conservative live-variable capture — this prediction was not tested against a 64-byte gate (no such gate was established). The original design predicted yield counts would match — the measured segment and settlement counts match, confirming equal turns though not identical suspension offsets. The original design predicted runtime overhead would be measurable — workflow CPU differences are within noise (−0.66% and −0.03%), and query CPU differences in single trials range from −9.83% to +0.20%, all exploratory.

(b) Determine whether the rewrite phase's input-reading cost (440.8 ms, the single largest component) can be reduced through caching or incremental compilation. (c) Evaluate the compile-time overhead in the context of on-device development iteration frequency.
